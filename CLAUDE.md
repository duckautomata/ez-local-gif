# ez-local-gif — notes for Claude Code

Self-hosted ezgif replacement. Read `docs/DESIGN.md` first — it is the source
of truth for architecture, Discord rules, encoder commands and the phase plan.

## Layout

- `cmd/ezlg` — main binary (`serve` default, `testkit`, `version`)
- `internal/recipe` — shared data model (Recipe/Op/Output/ProbeInfo); stdlib only, no ffmpeg
- `internal/graph` — op stack → ffmpeg filter_complex (pure, golden-tested; `alpha_ffmpeg_test.go` is an external `graph_test` package that pixel-checks the alpha chains against a real ffmpeg when one is on PATH, skipped otherwise)
- `internal/enc` — argv builders for ffmpeg/gifsicle/… (pure, golden-tested)
- `internal/fit` — fit-to-size search (ladder + secant over one knob; pure orchestration, fake-encoder tested)
- `internal/ffrun` — the only package that spawns processes; ffmpeg progress parsing
- `internal/discordlint` — GIF/WebP/APNG/static byte-level lint + fix, `MergeGIFHolds` (folds harmless no-op GIF frames into the previous frame's delay — jobs runs it on ffmpeg's GIF output before the gifsicle post-pass and inside the hold repair), `PlayGIF` / `GIFPlayback.Same` / `PrependTransparentFrame` (spec playback of a GIF, used to prepare and to check the gifsicle coalesce of the hold repair), `GIFNeedsCompleteFrames` / `DisposeCompleteFrames` (detect and repair ffmpeg's alpha GIF of a clip that mixes fully opaque and transparent frames: complete-frames second encode, disposal 2 on every frame, before the merge), plus Phase 4 structural MP4/WebM lint (`LintVideo`, `video.*` rules, no fixer); stdlib only
- `internal/probe` — ffprobe → ProbeInfo (+ alpha scan)
- `internal/store` — /data layout: blobs by sha256, results by recipe hash, scratch, sweeper
- `internal/jobs` — job table, SSE events, render pipeline
- `internal/server` — HTTP API + embedded SPA
- `web/` — Svelte 5 + Vite SPA; `web/dist` is embedded by `web/embed.go`

  If a shell was started before the install, refresh PATH first:
  `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`
  then plain `go vet ./...` / `go test ./...`. `.\scripts\go.ps1 …` still
  works as a Docker fallback (`golang:1.26-trixie`, repo mounted at /src).
- `ffmpeg`/`ffprobe` on the host are a 2026-08 FFmpeg git build (≥ 9.0.1
  features: animated WebP demuxer, libwebp_anim, prores) at
  `C:\Programs\bin\ffmpeg-master-latest-win64-gpl\bin`. ffmpeg 9.0.1 also
  exists in WSL (`wsl -e ffmpeg …`, host paths under `/mnt/c/...`).
- gifsicle / gifski / libwebp CLI / libavif / pngquant / oxipng are NOT on the
  host. The authoritative toolchain is the Docker runtime image — integration
  tests run there: `docker compose build && docker compose run --rm app …`.
- Node 22 / npm are on the host for `web/`.

## Rules

- Keep `internal/recipe`, `internal/graph`, `internal/enc`, `internal/discordlint` stdlib-only and process-free (except discordlint may use image/gif for pixel-index analysis).
- Do not change exported signatures in the stubs without updating every caller and the docs comment; prefer adding.
- Every ffmpeg/gifsicle argv change needs its golden test updated.
- Discord rules live in `docs/DESIGN.md` §5.3 and `internal/discordlint`; bump `discordlint.RulesVersion` when rules change.
- Results are memoised on disk under `jobs.ResultKey(recipe)` = hash(recipe, `jobs.PipelineVersion`, `discordlint.RulesVersion`). Bump `jobs.PipelineVersion` whenever graph/enc/jobs change what a recipe renders to, or users get stale cached outputs.
- Bump `store.InfoVersion` when probe semantics change (persisted ProbeInfo is re-probed on the next upload).
- Never use ffmpeg's legacy `libwebp` encoder for animation (use `libwebp_anim`); always pass `-loop 0` (webp) / `-plays 0` (apng).
- Every delivered ffmpeg GIF encode of frames with transparency passes `-gifflags -offsetting` (`enc.GIFArgs` alpha branch — the only GIF encode in the app — and `scripts/discord-testkit.sh`; `scripts/make-test-clip.sh` and `scripts/check-tools.sh` only make synthetic test files and do not): ffmpeg's bounding-box crop of transparent frames skips the box's bottom row in its column scans and cuts pixels off. ffmpeg also picks diffing + disposal per frame, which renders a clip that MIXES fully opaque and transparent frames wrong (holes in the opaque frames, which then stay under the transparent ones): `jobs.encodeGIFAt` detects the mix from the first encode's output (`discordlint.GIFNeedsCompleteFrames`: the encoder marks the two kinds with different disposals; an entirely transparent lead-in before opaque frames is exact and exempt) and only then encodes again with `enc.GIFOptions.CompleteFrames` (`-gifflags -offsetting-transdiff`) and runs `discordlint.DisposeCompleteFrames` (every frame disposal 2) before `MergeGIFHolds`. The two halves are only valid together — never run `DisposeCompleteFrames` on a `transdiff` encode (far worse than either defect), and do not make complete frames the default (fully opaque frames lose their diffing: several times larger without gifsicle). DESIGN.md §4.2 GIF row, §5.2 item 8; `TestGIFAlphaKeepsBottomRowEdgePixels`, `TestGIFAlphaOpaqueFramesAreComplete`, `TestRenderGIFMixedOpaqueFrames`, `TestEncodeGIFAtReencodesMixedClips`. The opaque path keeps the default flags — its diffing and diff crop are correct and keep those files small.
- GIF outputs must not contain a frame that leaves the picture unchanged but changes the disposal (rule `gif.noop-frame-disposal`; error for Discord targets, warning for target none): Discord drops such frames and their disposal with them, so the clear is lost and poses stack (DESIGN.md §5.2 item 9 — user-verified by upload, NOT reproducible with public lilliput, so the rule is the contract). gifsicle `-O1`/`-O2`/`-O3` make these frames out of holds and no flag avoids it. What the code does about it (DESIGN.md §5.3): `discordlint.MergeGIFHolds` runs on the **encoder's** output before gifsicle in `jobs.encodeGIFAt` (ffmpeg's `base.gif`, single renders and fit candidates) and on the coalesced file inside `jobs.repairGIFHolds` — any new `gifsicle -O` pass over freshly encoded frames must merge first. The lossless fast path and the optimize preset cannot pre-merge (frame selection / crop happen inside the same gifsicle call that optimises the *source's* holds), and the gifski loop pass and the ladder's `--colors` rung do not either: those rely on lint + the hold repair. A failed hold rule counts as a **structural failure at any level** (`jobs.hasStructuralError` / `onlyHoldsFailed` — also as a warning for target none), so `lintGIF` (render, fast path, gifski) repairs for every target and `repairIfOnlyHolds` (optimize preset, `optimizeFit`, default-encoder render-fit candidates) repairs when it is the *only* structural failure. gifski fit candidates walk the whole ladder (`jobs.gifLadder`, the function behind `lintGIF`): gifski's per-frame local colour tables fail `gif.frame0-transparency` for every target and only the `--colors` rung fixes that — anything that runs the ladder per fit candidate must pass a unique scratch tag (candidates encode concurrently in one directory). `jobs.repairGIFHolds` never trusts gifsicle's coalesce: it exits 0 on results that changed the picture (no transparency at all unless the FIRST frame declares and uses a transparent index — hence the transparent 1x1 lead-in frame, `discordlint.PrependTransparentFrame` + `enc.GifsicleOptions.SkipFirstFrame` = `#1-`, for every file that shows the background; and "too complex to unoptimize" with local colour tables / > 256 colours per picture, where it still stamps disposal 2) — the coalesced file, and step B when nothing lossy (`--lossy`/`--colors`) ran, is played and compared with the input (`discordlint.PlayGIF`, `GIFPlayback.Same`) and a changed picture is an error, never a repair (an input that cannot be played, or a result over `discordlint.ErrAnalysisCap`, goes unchecked). Any new gifsicle pass that is supposed to be lossless should be checked the same way. Never add a ladder rung that ends in plain `gifsicle -U` (it writes a disposal 0/2 mix and keeps the bad frames — coalesce with `-U --disposal=background` and no `-O`, then `MergeGIFHolds`).
- Alpha head: `yuva*` sources (ProRes 4444) unpremultiply at native depth and convert to rgba **once** (`setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,format=rgba`). Never route a yuva source through `gbrapNN` before rgba — ffmpeg-made ProRes stores alpha on the luma range and the gbrap copy leaves transparent pixels at alpha 1 (DESIGN.md §4.1). RGB-decoded sources keep `format=gbrap,setparams=…,unpremultiply`.
- The frame-master cap lives in `internal/jobs` only (`Options.MaxMasterBytes`, `admitScratch`/`admitReversed`); `internal/graph` never refuses a plan for its frame count (it reports `Plan.Width/Height/Frames` and forward stills/proxies are never gated on them), and nothing may allocate from `Plan.Frames` before admission — every consumer must stay a comparison or a float (DESIGN.md §4.1).
- chromakey key colour: ffmpeg's `chromakey` converts `color=0xRRGGBB` with full-range RGB→YUV coefficients but keys the limited-range chroma `format=yuva444p` carries (green: U 54/V 34 in the frame vs 44/21 for the key — 0.047 apart, so nothing below that similarity keyed, the exact colour included). The compiler emits the BT.601 **limited-range** `0xYYUUVV` with `:yuv=1` (one conversion helper in `internal/graph`, with its own test: Y = 16 + (65.481R + 128.553G + 24.966B)/255, U = 128 + (−37.797R − 74.203G + 112.0B)/255, V = 128 + (112.0R − 93.786G − 18.214B)/255, rounded; green → `913622`, blue → `29f06e`) in a working format **pinned** to BT.601 limited range — the stage is, verbatim, `format=rgba,format=yuva444p:color_spaces=bt470bg:color_ranges=tv,chromakey=color=0xYYUUVV:similarity=S:blend=B:yuv=1` (`graph.chromaKeyFormat`). The pin is what makes a tagged source key, not the rgba pass: libavfilter's colorspace / range negotiation carries the source's tags across the rgba link, so a bare `format=yuva444p` re-encodes a bt709-tagged capture (screen-recording MP4) with ITS matrix — measured on the host build: pure green came back U 42 / V 27 through `format=rgba,format=yuva444p` (U 42 / V 26 without the rgba pass), 0.047 from the 601 key, and did not key below ~0.05; with the pin every tagging (bt709 tv and pc, bt470bg, untagged, RGB, bt709 ProRes 4444) yields U 54 / V 35 and keys at 0.02. The leading `format=rgba` stays per the Phase 5a contract (through `ensureRGBA` inline; harmless when redundant); the despill type follows the RGB key. Never emit `0xRRGGBB` again, never emit a bare `format=yuva444p` before `chromakey` (never drop the `color_spaces=bt470bg:color_ranges=tv` pin), never drop the rgba pass, and keep `MinSimilarity` 0.01 (the dead zone was the range mismatch, not a floor). DESIGN.md §4.3 Background removal; pixel tests in `internal/graph/keying_ffmpeg_test.go` (`TestChromaKeyExactColourPixels`: RGB PNG, bt709 tv, bt709 pc, bt709 ProRes 4444 — all at similarity 0.02). Known consequence of the 0.1 default: chromakey averages the 3×3 neighbourhood, so a screen pixel with three subject neighbours scores a third of the subject's chroma distance (~0.17 for a saturated subject on green/blue) — above 0.1 + blend 0.05 — and a 1-px rim of (despilled) screen colour stays fully opaque along hard edges; ~0.15 keys it softly, 0.2 (the old default) keyed it. Documented in DESIGN.md §4.3 Defaults and the card's Screen hint; the tests pin the rim deliberately (`feather_ffmpeg_test.go`, `jobs/phase3_e2e_test.go`, `enc/phase3_ffmpeg_test.go`).
- `erosion` / `dilation` have **no `planes` option** (`coordinates`, `threshold0..3` only). The `morph` op works on gbrap (planes G,B,R,A) and freezes the colour planes with `threshold0=0:threshold1=0:threshold2=0` — `vf_neighbor.c` clamps each plane to `[p−threshold, p]` / `[p, p+threshold]`, so 0 leaves G/B/R byte-identical and the default `threshold3` (65535) makes A a plain 3×3 min/max — then `format=rgba`. Close = dilation then erosion; grow = extra dilations (0..4); at least one must be set. Hoisted with the keys/feather in stack order, skipped while `!c.hasAlpha` (feather's rule), a detection op (`graph.detectOps` + `jobs.detectionOps`), never the lossless fast path. DESIGN.md §4.3 Morph.
- Keying defaults live in **two** places and change together with a `jobs.PipelineVersion` bump: `internal/graph/phase3.go` (`defaultChromaSimilarity` 0.1, `defaultColorSimilarity` 0.08, blends 0.05 / 0) and `web/src/lib/state.svelte.ts` (`CHROMA_DEFAULTS` / `COLORKEY_DEFAULTS`). The SPA serialisers omit the default, so the Go zero value is what renders — a default moved on one side only silently renders every existing recipe differently from what the card shows. Multi-colour keys are N `colorkey` ops (no new op kind); the card's modes are None · AI · Colour · Screen (Phase 5a, and the 5b "AI" mode, built) — the AI mode stays opt-in and configurable (off without the sidecar; model and device chosen by the operator).
- AI matte (Phase 5b, DESIGN.md §4.3 AI matte row + §6): the matte identity enters the recipe hash **through `MatteParams.Resolved` filled by the server, never from the client** — `jobs.Submit` and the render strip any client-sent `Resolved` (`stripMatteResolved`) and fill it from the persisted facts `/data/mattes/models.json` (`fillMatteResolved`) before hashing, so `ResultKey` changes with the weights and a pulled sidecar image never serves a stale result; keep that order. The matte memo key (`matte.ClipKey`, salted by `matte.KeyVersion`) **never includes `jobs.PipelineVersion`** — a 20-minute CPU pass must survive app upgrades; bump `matte.KeyVersion` only when the producer chain, the frame hash or the memo layout changes. Every new consumer of a matte input in `internal/enc` (`extraInputArgsFor` / `matteInputArgs`, the `stillSeek.slot` plumbing) gets a golden. A forward still's matte input is ONE unlooped PNG — **never `-loop 1`** on it (an infinite image2 input costs a late still ~1.8 s); reversed CFR tail seeks shift `-start_number`, everything else reads the full sequence. The detection ops behind `autocropKey` canonicalise a matte op to its decoded `{model, size}` (`autocropDetectionOps`), so the previews' stripped op and the render's filled one share one memo. The sidecar's bare `missing` state (no reason, no lastError) is a download that has not started — pending, never a refusal; only `missing` after a failed download and `unavailable` refuse. The matte client's transport closes idle connections before the sidecar's 30 s socket timeout does (`matteIdleConnTimeout`): batch POSTs are not replayable.
