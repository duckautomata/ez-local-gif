## 1. Goals and priorities

- Self-hosted ezgif replacement, running as one Docker container on the LAN Linux box.
- Inputs: GIF, AVIF (static/animated), image sequences, MP4, MKV, MOV (Apple ProRes 4444 with alpha), WebP (static/animated), WebM.
- Outputs: animated GIF / WebP / APNG / AVIF with transparency, PNG frames, MP4/WebM, static images.
- Features: ProRes-alpha → GIF/WebP; extract frames; sequence → animation; crop/resize/compress;
  fit into Discord emote (256 KiB) / sticker (512 KiB) budgets with best quality; background removal
  (chroma key, pick-a-colour); overlay text / static image / looping animated image.
- Hard requirement: outputs must not render broken/black on Discord.
- Ranking: (1) speed end-to-end, (2) simple UI/UX.

## 2. Decision summary

| Area | Decision | Why |
|---|---|---|
| Where processing runs | Server-side, in the container. Browser = UI + native `<img>/<video>` preview + canvas for crop/overlay/eyedropper. | 200 MB ProRes crosses 1 Gbps LAN in ~2 s. ffmpeg.wasm is 12–25× slower than native, capped ~2 GB, multi-thread needs SharedArrayBuffer (HTTPS + COOP/COEP — not available on a plain `http://LAN-IP` page), no AVIF, no CUDA. |
| Backend | Go, one static binary, stdlib-mostly, frontend embedded via `embed`, all pixel work by `os/exec` of CLIs. | Single artifact, trivial goroutine concurrency, `exec.CommandContext` cancellation, tiny runtime layer. Go never touches pixels except the byte-level Discord linter. |
| Frontend | Svelte 5 + Vite (TypeScript), no component library. Built in a Docker stage, embedded in the binary. | Crop rectangle / drag-to-place overlays / eyedropper / reactive op stack need state; Svelte is the least boilerplate for that. (Vanilla ES modules with no build is acceptable if you prefer zero toolchain — the design does not depend on the framework.) |
| Media engine | FFmpeg **9.0.1** (BtbN static gpl build) as the only decoder/filter engine. | 9.0 (Aug 2026) is the first FFmpeg that natively decodes/demuxes **animated WebP**; ProRes 4444 alpha decodes on CPU to `yuva444p10le`; libwebp_anim, palettegen/paletteuse, apng, drawtext, chromakey/colorkey/despill, overlay all in one binary. |
| Encoders / optimizers | `gifsicle` 1.96, libwebp 1.5 tools (`img2webp`, `webpinfo`, `anim_dump`), libavif (`avifenc`/`avifdec`), `pngquant`, `oxipng`, `gifski` 1.34 (opt-in HQ only). | Each covers a corner FFmpeg does not (lossy GIF, indexed 8-bit-alpha APNG, alpha-safe AVIF, verify decoders). |
| Op model | Non-destructive op stack (trim, crop, resize, fps, key, overlays, text) compiled to **one** ffmpeg filtergraph. Preview and export share the compiler. | No generational loss (ezgif re-quantises the GIF at every step). Preview == output. |
| Render model | Per render: decode once → RGBA rawvideo master on tmpfs (`/dev/shm`) → fan out all encoders / fit candidates in parallel → delete. Results memoised on disk by hash(source, ops, output). | Fit-to-size needs many encodes of the same frames; ProRes must be decoded once, not per candidate. Cross-request frame caching is *not* done (premature). |
| Jobs | In-memory job table + SSE progress (`ffmpeg -progress pipe:1`). No DB, no broker, no auth, no TLS (LAN only, documented). | Progress feedback and cancellation for ~150 lines of Go. |
| Discord safety | Encode-by-construction rules **plus** a mandatory Go post-encode linter/fixer (GIF/WebP/APNG) **plus** decode-verify, before a download link appears. | Discord re-encodes every preview through `lilliput`; files that look fine in Chrome still break there. See §5. |
| GPU | Not in v1. Later: opt-in compose `gpu` profile (NVDEC for long/hi-res H.264/HEVC/VP9/AV1 sources, NVENC for MP4 export), and an optional `rembg` sidecar for AI matting. | NVDEC cannot decode ProRes; every GIF/WebP/APNG/AVIF encoder is CPU; CUDA context init (~200 ms) rivals total work on 128–320 px clips. |

### 2.1 Decisions confirmed by the user (2026-08-18)

- Stack: **Svelte + Vite** frontend, **Go** backend, deployed with **docker compose** (one `app` service — the SPA is embedded in the Go binary; an optional `rembg` Python sidecar for AI background removal is added to the same compose later under a `gpu` profile).
- Deployment targets (both have nvidia-container-toolkit, both drivers ≥ 610 → prebuilt FFmpeg 9 NVENC gate is satisfied):
  - **WSL2 on the Windows workstation** (RTX 5080, Windows driver 610.88 / CUDA 13.3). Zero network cost, same machine as DaVinci Resolve, best dev loop. Notes: keep `/data` on the WSL ext4 filesystem (a named volume or a path inside the distro), *not* under `/mnt/c` (9P is slow); an `/input` bind of a Windows export folder is fine for reading a few files; set `.wslconfig` `[wsl2] memory=` high enough that `shm_size 4g` + encoders fit (WSL defaults to 50 % of RAM); WSL's `nvidia-smi` prints its own version (580.x) but the driver version shown is the Windows one. Recent Windows drivers expose NVENC/NVDEC into WSL2 (verify: `ls /usr/lib/wsl/lib | grep -E 'nvcuvid|nvidia-encode'` and the container self-test); CUDA compute (rembg/onnxruntime) works.
  - **Bare-metal Linux box** (RTX 3070, driver 610.57.04 / CUDA 13.3). Always-on option; full NVENC/NVDEC (Ampere: no AV1 *encode*; AV1 decode ok). LAN upload cost ≈ 2 s per 200 MB.
  - Which is faster is decided by **CPU**, not GPU, for v1 (all animated-image encoders are CPU). The compose file is identical on both.
- Source material: **DaVinci Resolve → QuickTime, Apple ProRes 4444, Alpha Mode: Premultiplied.** → The "premultiplied source" toggle defaults **on**; `unpremultiply` runs at native bit depth right after decode (see §4.3). Bit depth is reported by ffprobe (`yuva444p10le` for 4444, `yuva444p12le` for 4444 XQ); all outputs are 8-bit anyway. If Resolve offers "Straight" alpha, prefer it (skips the unpremultiply, which loses precision in low-alpha edge pixels) — not required.

## 3. Architecture

```
Browser (Svelte SPA, embedded)                    Container (Go binary + CLIs)
┌──────────────────────────────┐   XHR multipart   ┌───────────────────────────────────────────┐
│ drop/paste/pick file(s)      │ ────────────────▶ │ /api/upload  → stream to disk, sha256,     │
│ still preview + scrubber     │ ◀──── PNG ─────── │   ffprobe, first still, 10 s low-res proxy │
│ preset chips                 │                   │ /api/still   → memoised (ops-hash, t, w)   │
│ op cards (collapsed)         │   POST /api/jobs  │ /api/jobs    → recipe → job → SSE events   │
│ result card + Discord check  │ ◀──── SSE ─────── │   compile ops → ONE filtergraph            │
│ download / save to /output   │                   │   ffmpeg → frames.rgba on /dev/shm         │
└──────────────────────────────┘                   │   fan-out encoders (semaphore NumCPU/2)    │
                                                   │   lint+fix → verify → /data/results/<hash> │
                                                   │ /out/<hash>/<file>  immutable              │
                                                   └───────────────────────────────────────────┘
Volumes: /data (blobs by sha256, results by recipe hash, TTL/LRU sweeper), /input (ro, optional),
/output (rw, optional), shm_size 4g.
```

Go packages (suggested): `cmd/ezlg`, `internal/graph` (op stack → filtergraph string + output dims;
golden-file tested), `internal/enc` (per-format argv builders), `internal/fit` (ladder + secant search),
`internal/discordlint` (GIF/WebP/APNG parse, fix, report), `internal/jobs` (table, SSE, cancellation),
`internal/store` (blobs, results, sweeper), `internal/probe` (ffprobe + alpha detection).

## 4. Processing model

### 4.1 Universal decode → master frames

```
ffmpeg -hide_banner -nostdin -y -threads 0 [-c:v libvpx-vp9  # only for VP9-alpha WebM]
  [-ss A -to B] -i SRC [overlay inputs...]                  # trim = input seek (µs-precise), except animated WebP sources (filter-level trim below)
  -filter_complex "[0:v][setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,format=rgba | format=gbrap,setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,]  # 'premultiplied source' toggle, hoisted: yuva* sources unpremultiply at native depth then convert ONCE to rgba; RGB-decoded sources go through gbrap (§4.3 Alpha)
     [trim=start=A[:end=B],setpts=PTS-STARTPTS,]              # webp_anim sources only (Plan.FilterTrim): FFmpeg 9's demuxer decodes nothing after an input seek
     [setpts=PTS/S,]fps=FPS:round=down                        # speed, then a drop that never lengthens the clip; Frames = floor(Duration*FPS + 1e-4) for video (trim bounds are µs-precise), exact integer grid maths for image sequences (graph.sequenceFrames)
     [,format=yuva444p,chromakey=...,despill=... | format=rgba,colorkey=...]  # background removal (full-res, 4:4:4); on frames that already carry alpha the key is wrapped: split, alphaextract both mattes, blend=all_mode=multiply, alphamerge (§4.3)
     [,crop=w:h:x:y]                                          # incl. a resolved autocrop
     ,format=gbrap,premultiply=inplace=1,scale=W:H:flags=lanczos,unpremultiply=inplace=1,format=rgba
     [,pad=CW:CH:(ow-iw)/2:(oh-ih)/2:color=0x00000000][,transpose|hflip|vflip]
     [output fit: scale / pad / crop to Output.Width x Output.Height]
     [,format=rgba,reverse]                                   # after the output fit: buffers output-sized 4 B/px frames, bounded by MaxMasterBytes (EZLG_MAX_MASTER_BYTES)
     [,format=rgba,split[f][r];[r]reverse[rr];[f][rr]concat=n=2:v=1:a=0]  # bounce (Phase 4): same slot as reverse, 2N frames / 2x duration, two buffered copies counted against MaxMasterBytes (§4.3); at most graph.MaxBounces (8) bounce ops per recipe — each doubles the buffered frames
     [,format=rgba,drawtext / overlay stages]                  # final-canvas ops in the order given; windows enable='gte(t+0.0001,S)*lt(t+0.0001,E)'
     ,format=rgba"
  -f rawvideo -pix_fmt rgba /dev/shm/ezl/<job>/frames.rgba      + meta.json {w,h,fps,n,has_alpha,durations}
```

- Every source type enters through the same `-i` (FFmpeg 9 handles GIF, animated WebP, APNG, MP4/MKV/MOV/WebM). **Image sequences (as built in Phase 2)** use the **image2** demuxer, not concat: the store renumbers frames to `%06d.<ext>` (png/jpeg/webp/bmp/tiff only), the graph emits `-f image2 -framerate 1000/delayMs -start_number 1 -reinit_filter 0` plus a leading `scale=W:H:force_original_aspect_ratio=decrease` guard (fftools otherwise rebuilds the filtergraph on any frame size/format change and the fps stage loses frames — verified), and mixed-size sequences additionally pad onto a transparent W×H canvas (`pad=…:eval=frame`). The `delay` op re-times the whole sequence (uniform delays; per-frame delay lists are a later phase).
- **AVIF ingest (verified on FFmpeg 9.0.1, Phase 2):** ffmpeg's mov demuxer exposes a still AVIF as [colour, alpha(gray)] and an **animated** AVIF (avifenc and ffmpeg's own muxer alike) as **four** video streams — the one-frame primary item (colour, alpha) *first*, then the animation tracks (colour, alpha). `[0:v]` therefore decodes the still item. The probe picks the colour stream with the most frames and records `ProbeInfo.ColorStream`/`AlphaStream` (v:N indices; e.g. 2/3 for an alpha animation, 0/1 for a still); the graph reads `[0:v:C]format=rgba[c];[0:v:A]format=gray[a];[c][a]alphamerge` (or just `[0:v:C]` when opaque). `avifdec --index all` remains available as a fallback (enc.AVIFDecArgs) but is not needed.
- `has_alpha` = ffprobe `pix_fmt`/`alpha_mode` probe **plus** a real min-alpha scan of the master (GIF decoder always reports BGRA; VP9-alpha WebM only shows alpha with `-c:v libvpx-vp9`).
- **Alpha head for yuva sources (as built 2026-08-22, verified on FFmpeg 9.0.1):** ProRes 4444 decodes to `yuva444p10le`/`yuva444p12le` (`color_range` tv), and ffmpeg-made clips — Resolve exports included — store alpha on the **luma range** (12-bit 256..3750) because swscale range-converts alpha together with luma for > 8-bit YUV. The earlier head `format=gbrap12le,…` copied alpha same-depth (a +7 drift, no range expansion) and the later rgba conversion left transparent pixels at alpha **1** with full RGB underneath: bigger files, and autocrop at threshold 1 saw the whole frame as content. Any `yuva*` source now gets `[setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,]format=rgba` — native-depth unpremultiply, then a single conversion to rgba (exact 0/128/255 alpha, colour within 1). RGB-decoded sources (PNG/GIF/WebP/AVIF) are unchanged (`format=gbrap,setparams=…,unpremultiply=inplace=1`). Never route a yuva source through `gbrapNN` before rgba.
- Lower-fps candidates re-read `frames.rgba` with `fps=`; no re-decode. **Reverse (as built)** is ffmpeg's `reverse` filter, not a Go reorder of the file: emitted after the output fit and before the final-canvas ops, preceded by `format=rgba`, so it buffers output-sized 4 B/px frames — bounded by `MaxMasterBytes` (`EZLG_MAX_MASTER_BYTES`). Frames and Duration are unchanged; text/overlay windows stay in output (reversed) time. See §4.3.
- **Frame-master cap (as built):** a render whose RGBA master (frames × W × H × 4 at output size) would exceed `jobs.Options.MaxMasterBytes` — env `EZLG_MAX_MASTER_BYTES`, bytes, default 2 GiB = 2147483648; ≤ 0 or unparsable → default — or the scratch filesystem is refused up-front with an actionable message ("trim the clip, lower the fps or resize the output"); renders that fit reserve their estimate from the scratch byte budget (minus what the still/proxy memo dirs hold, §4.3 Previews). The same cap bounds the reverse buffer and refuses reversed stills/proxies (400). The streaming bypass for larger sources (frames straight into the encoder, no master) remains a later item.
- Duplicate-frame merge: `mpdecimate` **with `-fps_mode vfr`** (otherwise ffmpeg re-duplicates the dropped frames) — still a later-phase item; Phase 2 sequences are CFR at the image2 `-framerate`.
- Time base: GIF delays are whole centiseconds; browsers clamp delays ≤10 ms to 100 ms → minimum 2 cs, so GIF fps is **capped at 50** (other formats at 60) and otherwise left alone: ffmpeg's gif muxer runs at a 1/100 s timebase and rounds each frame's pts, so a 30 fps master gets 3/3/4 cs delays with exact total timing (Bresenham for free) and no frames are dropped or duplicated. (An earlier draft snapped to 100/n rates; that duplicated 1 in 9 frames for 30 fps sources.)

### 4.3 Editing ops

- **Background removal:** `format=yuva444p,chromakey=color=0x00FF00:similarity=0.20:blend=0.05,despill=type=green:mix=0.6:expand=0.3` (blue: `0x0000FF`, `type=blue`); pick-a-colour: `format=rgba,colorkey=color=0xRRGGBB:similarity=S:blend=B`. Eyedropper reads the still-frame PNG in the browser canvas; sliders re-render the still (~100 ms). Applied before scaling at full res. AI matting (rembg/BiRefNet on CUDA) = optional Python sidecar later. **Keying on alpha-carrying frames (as built):** `chromakey`/`colorkey` *overwrite* the alpha plane, so when the incoming frames already carry alpha (source alpha, a merged AVIF alpha stream, transparent sequence padding, an earlier key) the compiler wraps the key — `split[k1][k1m];[k1m]alphaextract[k1a0];[k1]<key stages>,split[k1k][k1km];[k1km]alphaextract[k1a1];[k1a0][k1a1]blend=all_mode=multiply[k1a];[k1k][k1a]alphamerge` — so the two mattes are *intersected*: a Resolve ProRes 4444 export with Background removal keeps its source alpha instead of losing it. Opaque frames keep the bare `chromakey`/`colorkey`. Recipe semantics (`recipe.ChromaKeyParams`): `blend` 0 means the default 0.05 (a hard edge needs a small positive value such as 0.001); despill is emitted only when the key colour has a single dominant channel (green or blue) and is skipped otherwise, even with mix/expand set.
- **Feather (as built):** the `feather` op (`recipe.FeatherParams`: `radius` = Gaussian sigma in **source pixels**; the zero value means the default 3, valid 0.1–50, anything else is a compile error) softens the alpha edge with `format=gbrap,gblur=sigma=<R>:planes=8,format=rgba` — gbrap orders the planes G,B,R,A, so `planes=8` blurs *only the alpha plane*, and 8-bit gbrap↔rgba is a lossless plane repack (no range hazard). The stage is hoisted with the keying stages: emitted right after the keying ops and before any geometry (crop/autocrop/resize/canvas/flip/rotate), wherever it sits in the stack; multiple feather ops stack in stack order, interleaved with the keys per their stack order. Because it precedes the geometry, the radius scales with the image — a 3 px feather on a 720 px source is ~0.5 px after the emote fit. When the frame carries no alpha at that point the stage is skipped entirely — on an opaque source a feather that precedes every key is dropped, while one after a key always applies: blurring a constant-255 plane is a no-op that would waste two format conversions. Feather belongs to the detection ops (`graph.CompileDetect`) exactly like keying — it changes which alpha exceeds the autocrop threshold. UI label: "Feather — N px (soft edge ≈ 2–3×N)". GIF output thresholds the softened edge back to 1-bit alpha; WebP/APNG/AVIF keep it.
- **Text (as built in Phase 3):** `drawtext=textfile=<job>/t1.txt:expansion=none:font=<fontconfig family>:fontsize=N:fontcolor=0xRRGGBBAA:x=<anchor expr>:y=<anchor expr>[:borderw/bordercolor][:box=1:boxcolor:boxborderw][:line_spacing][:enable='gte(t+0.0001,S)*lt(t+0.0001,E)']`. The body goes through a text file (written by jobs, bound into the filter with two-level escaping) so user text renders verbatim — `expansion=none` is required or drawtext eats backslashes and expands `%{…}`; `font=` takes a bare fontconfig family (no quoting; unknown families fall back), listed by `GET /api/fonts` (`fc-list`; image ships DejaVu + Noto core, optional `/fonts` mount is a registered fontconfig dir). Anchors ("tl"…"br") resolve X/Y against `text_w/text_h`. **Time windows** (text and overlays) are half-open `[S, E)` like trim: the graph emits `enable='gte(t+0.0001,S)*lt(t+0.0001,E)'` (`'gte(t+0.0001,S)'` for an open end, nothing for the whole clip; ffmpeg's `between()` is inclusive at both ends and is not used) — the 1e-4 s tolerance absorbs the µs rounding of the bounds (a frame-grid start such as 2/30 → 0.066667 lies just above its frame's raw timestamp, which a plain `gte` would skip) and the SPA floors "from scrubber" bounds to whole µs, so adjacent windows `[A,B)`/`[B,C)` never overlap and the frame at exactly E is not drawn. **Non-opaque colours (as built):** drawtext blends alpha *in place* on the rgba canvas, so any RRGGBBAA colour with AA < ff (the default box colour `00000080` included) is drawn on a transparent `color` source layer per element group (box → border → glyphs), faded with `colorchannelmixer=aa=AA/255` and composited with `overlay=format=auto:shortest=1:eof_action=repeat[:enable=<window>]`; opaque colours keep the in-place drawtext. Note: the Windows host's gyan FFmpeg build crashes on any `font=` lookup (no fontconfig config) — text only works in the container.
- **Image overlay (as built):** overlay assets are ordinary uploads listed in `Recipe.Sources[1..]`; the graph emits one extra `-i` per asset (`[k:v]format=rgba[,fps=FPS][,premultiplied lanczos scale][,colorchannelmixer=aa=<opacity>],tpad=stop_mode=clone:stop=-1[ovk];[base][ovk]overlay=x=<anchor expr>:y=<anchor expr>:format=auto:shortest=1:eof_action=repeat[:enable='gte(t+0.0001,S)*lt(t+0.0001,E)']`). The `tpad` hold is mandatory (verified): without it `shortest=1` ends the whole output when a shorter overlay runs out, and without `shortest=1` a longer overlay extends it — with both, the base always decides the length and a finished overlay holds its last frame. Still images carried by image2/`*_pipe` demuxers get `-loop 1`; stills inside gif/apng/webp/mov containers reject `-loop` and rely on the hold.
- **Looping animated overlay (as built, verified on FFmpeg 9.0.1):** gif and video containers loop with `-stream_loop -1`; **animated WebP and APNG must use `-ignore_loop 0` instead — `-stream_loop -1` hangs FFmpeg 9's `webp_anim`/`apng` demuxers** (they never return after the seek-back), and with `-ignore_loop 0` the file's own loop count is obeyed (this app writes loop-forever files; a play-once file holds its last frame via the `tpad` hold). Non-looping overlays simply hold their last frame. Base alpha survives `overlay=format=auto` on an rgba main. VP8/VP9-alpha overlays force `-c:v libvpx`/`libvpx-vp9`; image sequences are not accepted as overlays (render them to an animation first). Stills: overlay inputs are not seeked — the main input keeps absolute timestamps (`-ss S -itsoffset …`) so overlays and `enable` windows line up exactly as in the render (`webp_anim` returns nothing after any `-ss`).
- **Trim on animated WebP sources (as built):** FFmpeg 9's `webp_anim` demuxer decodes nothing after an input seek, so for `webp_anim` sources the compiler emits a filter-level `trim=start=S[:end=E],setpts=PTS-STARTPTS` as the first stage (`Plan.FilterTrim`) instead of `-ss`/`-to`. Every `webp_anim` main-source plan, trimmed or not, is also flagged `Plan.SeekUnsafe` (FilterTrim implies it): stills and proxies never seek such plans — an untrimmed animated WebP still decodes in one unseeked ffmpeg run (jobs' `StillArgsFromStart` retry remains only as the guard for unexpected empty results), and a reversed proxy of one never seeks the tail, so its reverse-buffer admission counts the whole clip. Reversed stills of VFR animation sources (gif/apng/webp/avif, `Plan.SourceVFR`) decode from `TrimStart` instead of seeking by index; reversed *proxies* of the seekable ones (gif/apng/avif) get the plain grid-snapped tail seek whether trimmed or not. Every other source keeps the µs-precise `-ss`/`-to` input seek.
- **Crop to content (as built):** the `autocrop` op is resolved by jobs before compiling: a detection pass over the compiled **detection plan** (`graph.CompileDetect` + `enc.CropDetectPlanArgs`: source head, unpremultiply, trim/delay/speed/fps and the keying ops — wherever those sit in the stack, since the compiler hoists them in front of the geometry; a green-screen clip with Background removal therefore resolves to its subject, not the opaque frame) samples ~5 fps and takes the union box — alpha sources: `alphaextract,lagfun=decay=1,bbox=min_val=<threshold-1>` (exact "alpha ≥ threshold" box; `cropdetect` was rejected because it tests row/column *averages* and rounds odd offsets), opaque sources: `cropdetect=limit=24:round=2:reset=0`. The parser reads only `[Parsed_bbox_`/`[Parsed_cropdetect_` log lines. The raw box is memoised under `<Scratch>/autocrop/<key>.json`, keyed by (source, detection ops, threshold; `autocropKeyVersion` 3), and the padding is applied on read, so changing the padding never re-detects; the padded box is clamped to the frame and becomes an ordinary crop at the op's position; a flat/transparent clip resolves to the full frame. Concurrent requests for one key share a single pass, and the leader's pass continues (bounded by `autocropTimeout`, 5 min) even if the request that started it goes away, so the waiters — and the next request — get the result. Image sequences are detected through the same image2 input. The autocrop must precede any geometry op (crop/resize/canvas/flip/rotate); reverse/text/overlays neither reach the detection nor its key. Default suggestion for Emote (emoji render at ~22 px).
- **Reverse (as built):** ffmpeg's `reverse` filter (an odd number of `reverse` ops; two cancel), emitted after the output fit and before the final-canvas ops, preceded by `format=rgba`. The filter holds every frame until EOF, so it must see the *output-sized* frames: 4 B/px × W × H × frames, which `MaxMasterBytes` (`EZLG_MAX_MASTER_BYTES`) bounds — a reverse in front of the fit would buffer source-sized frames (a 1080p 60 s clip fit to 128 px: 28 GiB for a 0.1 GiB master). Frames and Duration are unchanged; for reversed plans output time t maps to source time `TrimStart + (Duration − t)·Speed` (stills/proxies, `Plan.Reversed`). Trim applies in source time, text/overlay windows in output (reversed) time. A single-frame source is left alone.
- **Bounce (Phase 4, ezgif "bounce"/ping-pong):** `recipe.OpBounce`, no params — play forward, then backward. Emitted in the same slot as reverse (after the output fit, before the final-canvas ops), preceded by `format=rgba`: `split[f][r];[r]reverse[rr];[f][rr]concat=n=2:v=1:a=0`. The output is a **simple full copy: exactly 2N frames and 2× the duration** (the first and last frames are duplicated at the joins — predictable and cheap; the trimmed 2N−2 variant was rejected as a surprise for frame counts). The plan reports the doubled Frames/Duration, so the fit engine, the frames export and the sticker ≤ 5 s check all see the doubled clip. Memory: the split buffers two output-sized copies — jobs counts the master estimate ×2 against `MaxMasterBytes` and the admission refuses what does not fit. Bounce and reverse compose in **stack order** (both emitted after the fit): a reverse in front of the first bounce reverses the forward half — `[reverse, bounce]` yields `rev(F)+F` (the clip opens on the *last* source frame) while `[bounce, reverse]` yields `F+rev(F)` — and reverse ops behind a bounce are dropped as identities (a full-copy bounce is a palindrome; reversing it reproduces it bit-identically, the reverse filter reusing the forward timestamps). A still source refuses bounce like it refuses reverse. Stills/proxies of a bounced plan are **never seeked** (decode from `TrimStart`, `SeekUnsafe`-like): output t < D maps to the forward pass, t ≥ D mirrors back. Autocrop is unaffected (bounce adds no pixels the forward pass lacks, like reverse it never reaches the detection). UI: a "Bounce (forward then back, doubles the length)" checkbox in the Speed card next to Reverse. `POST /api/still` (one PNG at t, ≤ maxW) and `POST /api/proxy` (the first `maxSeconds` of the op stack as a low-res animated WebP at ≤ 15 fps, lossy, with alpha; a single-frame plan with an animated overlay is proxied as an animation without the `fps=15` stage) share the compiler with the render and go through admission: reversed plans whose buffer would exceed `MaxMasterBytes` are refused (400, "trim the clip"; for a reversed proxy the buffer is the tail enc seeks to, or the whole clip for `Plan.SeekUnsafe` animated-WebP sources, which are never seeked); a preview semaphore of max(2, concurrency) bounds the ffmpeg runs; in-flight requests are de-duplicated by memo key (one render, every waiter gets the file). Results are memoised under `<Scratch>/stills` and `<Scratch>/proxy`, bounded by count (`MaxStills`) **and** bytes (`MaxStillsBytes`/`MaxProxyBytes`; oldest evicted), and the scratch budget for renders subtracts what those dirs hold.
- **Alpha:** the user's Resolve exports are **premultiplied** (matted with black), so the "premultiplied source" toggle defaults on for ProRes; the graph inserts `setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,format=rgba` immediately after decode for `yuva*` sources (ProRes 4444 decodes as `yuva444p10le`/`12le`; `unpremultiply` takes the yuva444p 9–16-bit variants directly, so the divide runs at native depth and the frames are converted to 8-bit RGBA exactly once — see §4.1 for why the earlier `format=gbrap1Nle` head was wrong for ffmpeg-made ProRes: alpha on the luma range, transparent pixels left at alpha 1) and `format=gbrap,setparams=alpha_mode=premultiplied,unpremultiply=inplace=1` for RGB-decoded sources, *before* any keying or scaling. Otherwise (WebP/APNG/AVIF need straight alpha) edges get dark fringes on light backgrounds. **The `setparams` tag is required on FFmpeg ≥ 8:** libavfilter now negotiates `AVFrame.alpha_mode` across links; `unpremultiply` demands premultiplied input but ProRes/rawvideo/most decoders tag frames `unspecified`, so without the tag ffmpeg auto-inserts `premultiply_dynamic` in front (`-loglevel verbose`: "auto-inserting filter 'auto_premultiply_dynamic_N'") and the pair cancels out — the toggle silently became a no-op (verified 9.0.1: edge pixel R=64/A=64 stayed R=63; with the tag R=253). Its position relative to the `format=` stage does not matter (the auto-inserted conversion passes the mode through). `internal/graph/alpha_ffmpeg_test.go` checks this at pixel level whenever ffmpeg is on PATH. A heuristic (edge pixels dark over white) pre-selects the toggle for other sources. Scale is wrapped in `format=gbrap,premultiply/…/unpremultiply`, which needs no tag: `premultiply` requires straight input, which is what `unspecified` degrades to (and after the hoisted unpremultiply the frames are tagged straight anyway). GIF = matte-then-threshold; WebP/APNG/AVIF keep 8-bit straight alpha.

### 4.4 Files in and out — /input picker, /output save (Phase 4)

Two optional bind mounts let files skip the browser: `/input` (read-only source folder) and
`/output` (bulk sink; also where the Discord test kit writes). Paths are configurable —
`EZLG_INPUT` (default `/input`), `EZLG_OUTPUT` (default `/output`). The server checks both **once
at startup** (directory exists, `/input` readable, `/output` writable) and reports the outcome in
`GET /api/capabilities` as `features.inputPick` / `features.outputSave`; the endpoints answer
**503** when their feature is off. Listing/writing is per-request — files added to a mounted
`/input` show up without a restart — and a directory that stops being usable *after* startup
(mount vanished, permissions, disk full) maps onto the **same operator-facing 503** as the
startup check, never a 500 leaking server-side paths (capabilities keeps reporting the startup
outcome until a restart).

- `GET /api/input` → `{"files": [{"name": "clip.mov", "size": 123, "mtime": "<RFC 3339>"}, …]}` —
  a **flat** listing (no recursion), filtered to extensions the pipeline can decode, name-sorted,
  capped at 500 entries, always an array (never null). (The Phase 4 draft sketched a bare array;
  it ships wrapped in `{"files": …}` for consistency with `/api/fonts` and the `{"error": …}`
  error shape.)
- `POST /api/sources/from-input` `{"name": "clip.mov"}` → 200 `recipe.Source`: ingests the file
  exactly like an upload (copy into the blob store, sha256 dedupe, probe) — re-picking a file, or
  picking one that was also uploaded, yields the same source hash. `name` must exactly match a
  listed entry (anything containing a path separator, or not in the listing, is 404 — that is the
  whole path-traversal defence); 503 when `/input` is off; a file over the upload size limit
  (`EZLG_MAX_UPLOAD_MB`) is 413, exactly like an upload of the same bytes.
- `POST /api/results/{recipeHash}/save` `{"file": "<name from the result manifest>", "name":
  "<optional base name>"}` → 200 `{"name": "<final file name>"}`: writes that result file into
  `/output` under a **collision-safe** name (`base.ext`, `base-2.ext`, `base-3.ext`, …; the base
  defaults to the download name the file would get with `?dl=1`) and returns the name actually
  used — 409 never happens. 404 for an unknown result or file name; 503 when `/output` is off.
- Web: the result card (and each batch row) gains "Save to /output" when `features.outputSave`;
  batch adds "Save all to /output". The upload zone offers "… or pick from /input" when
  `features.inputPick`. There is no zip-of-everything endpoint — downloads stay per-file,
  `/output` is the bulk sink.

### 5.2 Why transparent files break on Discord (from `discord/lilliput` source)

Every inline preview (attachments, emoji, stickers) is decoded and re-encoded server-side by lilliput (giflib + libwebp + libavif). Known quirks as of Aug 2026:

1. GIF frame **without a Graphic Control Extension** → transparent index uninitialised (usually palette index 0) → wrong/flickering colours (issue #267, fix PR #276 unmerged).
2. Canvas background alpha is decided **only from frame 0's GCE**: if frame 0 has no transparency flag the canvas is opaque (LSD background colour) and later transparent frames get a solid (often black) background — the classic symptom. The encoder also deletes transparency for a frame whose transparent index equals the LSD background index when the background is opaque.
3. Disposal 0 (unspecified) treated as "do not dispose"; disposal 3 (restore previous) only supported since Apr 2025; disposal/background handling churned May 2025.
4. Missing NETSCAPE2.0 loop block → loop count 1 (plays once) after GIF→WebP transcode.
5. Frame-diff optimised GIFs / per-frame local palettes have produced "random colour per frame" glitches (local-palette corruption fixed Jun 2025; still cited in 2025 reports).
6. WebP: alpha is dropped if the VP8X container **ALPHA flag** is unset while frames carry alpha (PR #296 open); wrong VP8X canvas dims broke uploads; Discord's EXIF stripper used to corrupt animated WebP metadata (fixed) → emit no EXIF/XMP/ICC.
7. First frame is shown as the still whenever animation isn't playing (autoplay off, reduced motion, hover previews) → a blank first frame looks broken.
8. ffmpeg foot-guns: legacy `libwebp` encoder → ghost trails; webp muxer `-loop` default 1; apng muxer `-plays` default 1.

### 5.3 Encoder rules → enforced by `internal/discordlint` (lint → fix → verify)

**GIF**
- GCE on every frame **including frame 0**.
- If any frame is transparent: frame 0's GCE has the transparency flag set (allocate an unused index if needed) and LSD background index = that transparent index. If nothing is transparent, LSD bg index ≠ any frame's transparent index.
- Explicit disposal 1 or 2 on every frame; never 0 or 3.
- NETSCAPE2.0 loop block present; count 0 for every Discord target (Discord plays once otherwise). For non-Discord output (target none) the user's `Output.Loop` (N = play N+1 times) is honoured and only the block's presence is enforced. Delays ≥ 2 cs (guaranteed by the 50 fps cap; the muxer's centisecond rounding gives exact Bresenham timing).
- Single global palette, no local colour tables (enforce via `gifsicle --colors N`; fail lint otherwise). No interlacing; strip comment/plain-text/app extensions.
- 1-bit alpha via matte-then-threshold; first frame representative (warn if empty).
- Fixer scope: add/patch GCE, flag/index, delay, disposal 0→1, LSD bg index, NETSCAPE, strip extensions. **Cannot** fix disposal 3, interlace, full palette with no free slot, local tables → re-encode ladder: `gifsicle -O2 --lossy --careful --colors N` → `-U -O2 --careful` → `-U` (coalesced full frames, disposal 2).

**WebP**
- WebPAnimEncoder paths only (`libwebp_anim`, `img2webp`, `gif2webp`); loop count 0 for Discord targets (target none: `Output.Loop` N → ANIM plays N+1, informational only); no metadata; VP8X present with ALPHA **iff** frames have alpha, ANIM iff n > 1 (a single-frame master is written as a plain still WebP via `-c:v libwebp`); canvas == frame size; every ANMF inside canvas; never re-mux with tools that rewrite VP8X. Frame durations: ≤ 10 ms is a warning (browsers show 100 ms), 11–19 ms an info note, ≥ 20 ms clean. Verify with `webpinfo`/`anim_dump` (libwebp — what Discord uses) and FFmpeg 9.
- Keep Discord WebPs small (Emote 128², chat default ≤ 480 px with a warning above).

**APNG (stickers only)**
- `acTL num_plays = 0` (Discord targets; target none reports the count); first frame is a real fcTL frame; all fcTL rects inside the IHDR canvas (dims > 320 on a side is a sticker *warning* — Discord shrinks); zero delays are a sticker error; delays ≤ 10 ms warn (browsers show 100 ms), 11–19 ms get an info note, ≥ 20 ms clean; ≤ 5.0 s; ≤ 1000 frames; ≤ 60 fps; ≤ 524,288 B. Invalid fcTL dispose/blend ops and tRNS-before-PLTE fail the container check (libpng rejects / drops alpha). UI: "APNG animates only as a server sticker, not as a chat attachment; never for emoji."

**Video — MP4 / WebM (Phase 4; attachment targets only)**
Video output is offered for target none and the attachment tiers **only** — never emote/sticker
(Discord takes no video there); a recipe combining `mp4`/`webm` with an emote/sticker target is a
400. `LintVideo` is a **structural** lint (no fixer — the encoders are safe by construction;
`Report.Format` is `"mp4"` / `"webm"`), rule ids (in this row order):
- `video.container` — error: MP4 `ftyp` with a known brand + `moov` + `mdat` and a clean top-level
  box stream / WebM EBML `DocType == "webm"` + Segment and a clean element stream; trailing bytes
  after the last box/element fail it (truncation/garbage detection).
- `video.faststart` — warn, mp4 only: `moov` precedes `mdat` (`-movflags +faststart` worked);
  omitted when `moov` or `mdat` is missing.
- `video.codec` — error: the video stream is H.264 `avc1`/`avc3` (mp4) / `V_VP9` (webm);
  informational pass when undetectable.
- `video.dims` — warn: width and height are both even and no side exceeds 4096; informational
  pass when unparsed (never blocks `Report.OK`).
- `video.duration` — info, always a pass: duration/frames/fps as parsed (0 = unknown).
- `video.size-limit` — error: bytes ≤ the target's cap (attachment tiers; omitted for target none).
- `video.attachment-only` — error: fails for emote/sticker targets ("video formats cannot be
  emotes/stickers"); passes for attachment tiers, omitted for target none.
RulesVersion is unchanged by Phase 4 — LintVideo is additive and no rule for an existing format
moved.

**Verify** (Discord targets): decode with two decoders (ffmpeg + Go GIF compositor emulating lilliput's semantics / libwebp `anim_dump` / `apngdis`), check frame count/dims, and a *tolerant* comparison (mean colour error or SSIM on ~8 sampled frames over `#313338` and `#FFFFFF`) — not a strict pixel-mismatch threshold (lossy/1-bit/dithered output always differs). On failure → coalesce fallback and re-fit. Show the lilliput-simulated preview in the result card. Stamp the lint ruleset version into `report.json`.

### 5.4 Presets and fit-to-size

Byte caps are hard, expressed in KiB, with a 1–2 % margin. Fit = parallel ladder from one master + secant search on log(size) over the format's quality knob (GIF: `gifsicle --lossy` 0–200, or gifski `--quality` 100→1 with the gifski encoder; WebP: `-q` 95–10; APNG: colours 256→64; AVIF: `-q`; MP4: x264 CRF searched 12..40 (mild probe = the effective CRF — Output.Quality-as-CRF clamped into the window, default 20 — harsh 40); WebM: vp9 CRF searched 15..55 (mild = effective CRF, default 30; harsh 55) — CRF is monotonic on log(size), so the same secant applies), 2 probes per rung (mild/harsh), skip rungs whose harsh probe is over budget, early-exit rungs whose mild probe fits, ≤ 5 iterations otherwise. Winner = mildest rung that fits; 2 runner-ups shown as alternatives; report the binding knob ("fit at 20 fps · 128 colours · lossy 40").

Perceptual cost order (cheapest first): autocrop/merge duplicates → ordered dither instead of error diffusion (−15–20 %) → lossy 30–80 (−20–40 %, near-invisible) → fps 30→24→20→15 → colours 256→128→64 → heavy lossy / alpha_q → downscale (never for stickers) → trim duration (ask).

Sticker 320² APNG pal8 (cartoon): 30 fps 666 KB, 15 fps 332 KB. → A 6–12-candidate fit search finishes in ~3–5 s wall on a 16-thread CPU.

## 6. GPU verdict

- **Cannot help:** ProRes decode (no NVDEC; FFmpeg 8.1+ has a *Vulkan* ProRes hwaccel, not CUDA — CPU decode is already fast and multithreaded), palettegen/paletteuse, gif/apng/libwebp/libaom/libsvtav1 encoders, gifski, gifsicle, avifenc, pngquant, oxipng — all CPU.
- **Can help later:** NVDEC for H.264/HEVC/VP9/AV1 sources ≥ 1080p or ≥ 10 s (`-hwaccel cuda` alone — auto-download to system frames; or `hwdownload,format=nv12` before the first CPU filter; never for alpha sources), NVENC for MP4/WebM(AV1) export, and **AI background removal** (rembg/BiRefNet on onnxruntime-gpu) — the one place the GPU would shine.
- Packaging: the BtbN FFmpeg 9 build already contains nvenc/nvdec/cuda-llvm at zero image cost. `gpu` compose profile: `gpus: all`, `NVIDIA_DRIVER_CAPABILITIES=compute,video,utility`; **host driver ≥ 610** for prebuilt 9.0 NVENC (≥ 570 for 8.x). Startup self-test `ffmpeg -f lavfi -i nullsrc -c:v h264_nvenc -frames:v 1 -f null -` greys out GPU options.

Within ~1 s: probe badge (format, W×H, fps, frames, duration, alpha yes/no) + still preview over checkerboard / Discord dark `#313338` / white. "Use for" chips: **Emote · Sticker · Chat (GIF/WebP/AVIF/MP4/WebM) · Optimize (GIF sources) · Frames · Custom** — MP4/WebM (Phase 4) appear for the Chat and Custom presets with attachment targets or none only (never emote/sticker; both are opaque, matted, audio dropped) — a preset pre-fills the Output card (canvas, format, fit, default Discord target) but the **Discord target dropdown stays editable** (none / emote / sticker / attachment free 20 MB / 50 MB / 100 MB / 500 MB). The top-left logo resets to the landing page. Op cards below, collapsed: Trim · Crop (drag rectangle with 8 edge/corner resize handles and a "Lock ratio" checkbox — it captures the current w:h and constrains resizes, new rectangles and the W/H inputs) · Resize/Canvas · Speed/FPS (+ Reverse · Bounce) · Background (eyedropper + tolerance/despill) · Feather ("Feather — N px (soft edge ≈ 2–3×N)", radius in source pixels) · Overlay (text / image / animated, drag to place, time range) · Output (format, quality or "fit to" bytes, Advanced fold). Result card: size badge green/red vs limit, W×H/frames/fps/duration, "fit at …", Discord-check list, preview on dark/light + 22/48 px emote and 160 px sticker "as seen in chat" thumbnails, Alternatives, Download (drag-out into Discord), Save to `/output` (when `features.outputSave`, §4.4), "Use as source" to chain. "Copy PNG" only when `window.isSecureContext` (Async Clipboard API is unavailable on a plain `http://LAN-IP` page; animated formats can't be copied anyway).

**Batch (Phase 4)** — same preset for several files, web-only orchestration (no new job machinery):
dropping/picking several video/animation files enters batch mode (several *images* keep their

## 8. Speed strategy

Ingest: XHR multipart (no tus/chunking), streamed to disk with SHA-256 computed server-side (WebCrypto is unavailable on plain HTTP), deduped by hash; probe + still + proxy pre-warmed the moment the upload lands; `/input` picker skips upload. Processing: one decode + one filter pass per render into the RGBA master on tmpfs; every encoder/candidate/format fans out from it under a `NumCPU/2` semaphore with `-threads 0`; encoder knobs pinned to fast settings (heavy squeezes — `-m 6`, zopfli, `apngopt` — behind an explicit button); GIF→GIF edits never decode; stills served from the master when it exists (Go `image/png`, no ffmpeg spawn); stills and Play proxies memoised on scratch behind admission (preview semaphore max(2, concurrency), in-flight de-duplication by memo key, count- and byte-bounded memo dirs — §4.3 Previews); results memoised by recipe hash. Delivery: files written once, served immutable, direct links, zips STORE'd, `/output` mount.

5. FFmpeg 9.0.1 static build: `webp_anim` demuxer/decoder on real files (alpha, durations, `-ignore_loop 0`); mov demuxer alpha stream for animated AVIF; `-hwaccel cuda` auto-download; drawtext with fontconfig; `libwebp_anim` with n == 1.
   **Verified ffmpeg facts** (FFmpeg 9.0.1 in the image; Phase 1–3 builds, last updated 2026-08-22 — each is pinned by a test or by the build-time `scripts/check-tools.sh` guard):
   - `setparams=alpha_mode=premultiplied` must precede `unpremultiply` (FFmpeg ≥ 8 otherwise auto-inserts a cancelling `premultiply_dynamic`; `internal/graph/alpha_ffmpeg_test.go`).
   - ffmpeg-made ProRes 4444 (`yuva444p12le`, range tv) stores alpha on the **luma range**; `format=gbrap12le` copies it same-depth (+7, no expansion) and the later rgba conversion leaves transparent pixels at alpha 1. `unpremultiply=inplace=1` runs on `yuva444p10le`/`12le` directly and a single `format=rgba` afterwards yields exact 0/128/255 alpha with colour within 1 (§4.1 alpha head).
   - `chromakey`/`colorkey` overwrite the alpha plane — the keying wrapper (split / alphaextract / `blend=all_mode=multiply` / alphamerge) is what keeps source alpha (§4.3).
   - `webp_anim` demuxer: decodes nothing after an input seek (`-ss`), for the main input and overlay inputs alike (filter-level trim; unseeked stills/proxies); `-stream_loop -1` hangs `webp_anim` and `apng` (use `-ignore_loop 0`, which obeys the file's own loop count).
   - `overlay=…:shortest=1:eof_action=repeat` plus `tpad=stop_mode=clone:stop=-1` on every finite overlay input: the base decides the length, a finished overlay holds its last frame.
   - `drawtext` blends alpha in place on an rgba canvas — semi-transparent colours need a separate `color` layer + `colorchannelmixer=aa=` + `overlay` (§4.3 Text).
   - `reverse` holds every input frame until EOF: memory = frames × W × H × 4 at the point it sits → after the output fit, under `MaxMasterBytes`.
   - `alphaextract,lagfun=decay=1,bbox=min_val=T-1` gives the exact alpha ≥ T union box; `cropdetect` averages rows/columns and rounds odd offsets; only `[Parsed_bbox_`/`[Parsed_cropdetect_` log lines carry the result.
   - `between()` is inclusive at both ends; `gte(t+0.0001,S)*lt(t+0.0001,E)` gives half-open windows and absorbs the µs rounding of frame-grid bounds.
   - The Windows host's gyan git build crashes on `drawtext font=` (no fontconfig config) — host test runs skip drawtext pixel checks; the image is authoritative.
6. Indexed 8-bit-alpha APNG without a custom muxer (does `-pix_fmt pal8` apng keep PLTE+tRNS and inter-frame diffs?).
7. Real timings on the server CPU for gifsicle/gifski/avifenc(aom vs svt)/pngquant/oxipng; whole fit search ≤ 5 s.
8. Your ProRes 4444 exports: known premultiplied (Resolve setting). Confirm bit depth with `ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,pix_fmt,width,height,r_frame_rate -of default=nw=1 file.mov` and eyeball an edge over white after `unpremultiply` (no dark halo = correct).
9. tmpfs sizing (1080p RGBA = 8.3 MB/frame; Docker default `/dev/shm` is 64 MB → `shm_size: 4g`, fallback `/data/tmp`; on WSL2 also raise `.wslconfig` memory). `EZLG_MAX_MASTER_BYTES` (default 2 GiB) caps one render's master — and the reverse buffer — and should stay below `shm_size`; the server warns at startup when scratch is smaller than the cap, and refuses renders over either up-front (§4.1).
10. GPU (only when the gpu profile is wanted): drivers are ≥ 610 on both machines; on WSL2 confirm `libnvcuvid`/`libnvidia-encode` are present under `/usr/lib/wsl/lib` and the in-container `h264_nvenc` self-test passes.

## 11. Risks

- Discord's lilliput/media proxy keeps changing (open PRs, 2025 disposal churn) → linter rules are data, versioned, re-validated per phase.
- FFmpeg 9.0.1 is weeks old (new webp_anim decoder) → fallbacks documented (`anim_dump`, `avifdec`), pin the tarball hash.
- Frame master sizing for long/hi-res chat exports → frame cap + streaming bypass + `shm_size` guidance.
- Animated AVIF alpha and GIF stickers unverified on Discord → labelled experimental; APNG stays the sticker default.
- Frame-diff GIF optimisation may still glitch through Discord in edge cases → verify step + coalesce fallback (costs bytes on a tight 256 KiB fit).
- Premultiplied vs straight alpha can't be auto-detected reliably → toggle + heuristic + dark/light preview.
- LAN-only assumptions (no auth/TLS) — keep behind the LAN or a reverse proxy.
- Licensing: gifski (AGPL) and gifsicle (GPL) are exec'd, not linked; cgo-linking gifski later would make the binary AGPL-derived.
- drawtext escaping/fonts (use `textfile=`, bundle fonts, add noto for CJK/emoji).

## 12. Rejected alternatives

Client-side WASM (ffmpeg.wasm/wasm-vips/gifski-wasm); Python/FastAPI main backend (kept only for an optional rembg sidecar); Node/Bun + sharp; Redis/Celery/SQLite job queues; ezgif-style per-tool pages with re-encoded intermediates; gifski as default GIF encoder; legacy ffmpeg `libwebp` encoder; CUDA-first pipeline; ImageMagick for animation; libvips via cgo; tus/chunked uploads; client-side hashing; WebSockets (SSE suffices); linuxserver/jrottenberg nvidia base images (700 MB–1.3 GB vs ~500 MB trixie-slim + static builds); APNG for chat/emoji; Lottie stickers; forking existing projects (ConvertX, OmniTools, imgproxy, gifcurry — borrow ideas only).
