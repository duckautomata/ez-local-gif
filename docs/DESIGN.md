## 1. Goals and priorities

- Self-hosted ezgif replacement, running as one Docker container on the LAN Linux box.
- Inputs: GIF, AVIF (static/animated), image sequences, MP4, MKV, MOV (Apple ProRes 4444 with alpha), WebP (static/animated), WebM.
- Outputs: animated GIF / WebP / APNG / AVIF with transparency, PNG frames, MP4/WebM, static images.
- Features: ProRes-alpha → GIF/WebP; extract frames; sequence → animation; crop/resize/compress;
  fit into Discord emote (256 KiB) / sticker (512 KiB) budgets with best quality; background removal
  (chroma key, pick-a-colour); overlay text / static image / looping animated image.
- Hard requirement: outputs must not render broken/black on Discord.
- Ranking: (1) speed end-to-end, (2) simple UI/UX.

## 2. Decision summary

| Area | Decision | Why |
|---|---|---|
| Where processing runs | Server-side, in the container. Browser = UI + native `<img>/<video>` preview + canvas for crop/overlay/eyedropper. | 200 MB ProRes crosses 1 Gbps LAN in ~2 s. ffmpeg.wasm is 12–25× slower than native, capped ~2 GB, multi-thread needs SharedArrayBuffer (HTTPS + COOP/COEP — not available on a plain `http://LAN-IP` page), no AVIF, no CUDA. |
| Backend | Go, one static binary, stdlib-mostly, frontend embedded via `embed`, all pixel work by `os/exec` of CLIs. | Single artifact, trivial goroutine concurrency, `exec.CommandContext` cancellation, tiny runtime layer. Go never touches pixels except the byte-level Discord linter. |
| Frontend | Svelte 5 + Vite (TypeScript), no component library. Built in a Docker stage, embedded in the binary. | Crop rectangle / drag-to-place overlays / eyedropper / reactive op stack need state; Svelte is the least boilerplate for that. (Vanilla ES modules with no build is acceptable if you prefer zero toolchain — the design does not depend on the framework.) |
| Media engine | FFmpeg **9.0.1** (BtbN static gpl build) as the only decoder/filter engine. | 9.0 (Aug 2026) is the first FFmpeg that natively decodes/demuxes **animated WebP**; ProRes 4444 alpha decodes on CPU to `yuva444p10le`; libwebp_anim, palettegen/paletteuse, apng, drawtext, chromakey/colorkey/despill, overlay all in one binary. |
| Encoders / optimizers | `gifsicle` 1.96, libwebp 1.5 tools (`img2webp`, `webpinfo`, `anim_dump`), libavif (`avifenc`/`avifdec`), `pngquant`, `oxipng`, `gifski` 1.34 (opt-in HQ only). | Each covers a corner FFmpeg does not (lossy GIF, indexed 8-bit-alpha APNG, alpha-safe AVIF, verify decoders). |
| Op model | Non-destructive op stack (trim, crop, resize, fps, key, overlays, text) compiled to **one** ffmpeg filtergraph. Preview and export share the compiler. | No generational loss (ezgif re-quantises the GIF at every step). Preview == output. |
| Render model | Per render: decode once → RGBA rawvideo master on tmpfs (`/dev/shm`) → fan out all encoders / fit candidates in parallel → delete. Results memoised on disk by hash(source, ops, output). | Fit-to-size needs many encodes of the same frames; ProRes must be decoded once, not per candidate. Cross-request frame caching is *not* done (premature). |
| Jobs | In-memory job table + SSE progress (`ffmpeg -progress pipe:1`). No DB, no broker, no auth, no TLS (LAN only, documented). | Progress feedback and cancellation for ~150 lines of Go. |
| Discord safety | Encode-by-construction rules **plus** a mandatory Go post-encode linter/fixer (GIF/WebP/APNG) **plus** decode-verify, before a download link appears. | Discord re-encodes every preview through `lilliput`; files that look fine in Chrome still break there. See §5. |
| GPU | Not for the app's own pipeline in v1. Later: opt-in compose `gpu` profile (NVDEC for long/hi-res H.264/HEVC/VP9/AV1 sources, NVENC for MP4 export). **AI matting runs on the GPU since Phase 5b** through the separate matte sidecar (`matte-gpu` profile, its own device reservation; `matte` = the same on CPU) — §6. | NVDEC cannot decode ProRes; every GIF/WebP/APNG/AVIF encoder is CPU; CUDA context init (~200 ms) rivals total work on 128–320 px clips. The matte is the one place the GPU pays: 18 ms/frame vs 136 ms on 8 cores. |

### 2.1 Decisions confirmed by the user (2026-08-18)

- Stack: **Svelte + Vite** frontend, **Go** backend, deployed with **docker compose** (one `app` service — the SPA is embedded in the Go binary; since Phase 5b an optional **matte sidecar** for AI background removal — `sidecar/`, ~stdlib Python + onnxruntime, no rembg, no torch — in the same compose behind the `matte` / `matte-gpu` profiles, off by default; §6).
- Deployment targets (both have nvidia-container-toolkit, both drivers ≥ 610 → prebuilt FFmpeg 9 NVENC gate is satisfied):
  - **WSL2 on the Windows workstation** (RTX 5080, Windows driver 610.88 / CUDA 13.3). Zero network cost, same machine as DaVinci Resolve, best dev loop. Notes: keep `/data` on the WSL ext4 filesystem (a named volume or a path inside the distro), *not* under `/mnt/c` (9P is slow); an `/input` bind of a Windows export folder is fine for reading a few files; set `.wslconfig` `[wsl2] memory=` high enough that `shm_size 4g` + encoders fit (WSL defaults to 50 % of RAM); WSL's `nvidia-smi` prints its own version (580.x) but the driver version shown is the Windows one. Recent Windows drivers expose NVENC/NVDEC into WSL2 (verify: `ls /usr/lib/wsl/lib | grep -E 'nvcuvid|nvidia-encode'` and the container self-test); CUDA compute (rembg/onnxruntime) works.
  - **Bare-metal Linux box** (RTX 3070, driver 610.57.04 / CUDA 13.3). Always-on option; full NVENC/NVDEC (Ampere: no AV1 *encode*; AV1 decode ok). LAN upload cost ≈ 2 s per 200 MB.
  - Which is faster is decided by **CPU**, not GPU, for v1 (all animated-image encoders are CPU). The compose file is identical on both.
- Source material: **DaVinci Resolve → QuickTime, Apple ProRes 4444, Alpha Mode: Premultiplied.** → The "premultiplied source" toggle defaults **on**; `unpremultiply` runs at native bit depth right after decode (see §4.3). Bit depth is reported by ffprobe (`yuva444p10le` for 4444, `yuva444p12le` for 4444 XQ); all outputs are 8-bit anyway. If Resolve offers "Straight" alpha, prefer it (skips the unpremultiply, which loses precision in low-alpha edge pixels) — not required.

## 3. Architecture

```
Browser (Svelte SPA, embedded)                    Container (Go binary + CLIs)
┌──────────────────────────────┐   XHR multipart   ┌───────────────────────────────────────────┐
│ drop/paste/pick file(s)      │ ────────────────▶ │ /api/upload  → stream to disk, sha256,     │
│ still preview + scrubber     │ ◀──── PNG ─────── │   ffprobe, first still, 10 s low-res proxy │
│ preset chips                 │                   │ /api/still   → memoised (ops-hash, t, w)   │
│ op cards (collapsed)         │   POST /api/jobs  │ /api/jobs    → recipe → job → SSE events   │
│ result card + Discord check  │ ◀──── SSE ─────── │   compile ops → ONE filtergraph            │
│ download / save to /output   │                   │   ffmpeg → frames.rgba on /dev/shm         │
└──────────────────────────────┘                   │   fan-out encoders (semaphore NumCPU/2)    │
                                                   │   lint+fix → verify → /data/results/<hash> │
                                                   │ /out/<hash>/<file>  immutable              │
                                                   └───────────────────────────────────────────┘
Volumes: /data (blobs by sha256, results by recipe hash, TTL/LRU sweeper), /input (ro, optional),
/output (rw, optional), shm_size 4g.
```

Go packages (suggested): `cmd/ezlg`, `internal/graph` (op stack → filtergraph string + output dims;
golden-file tested), `internal/enc` (per-format argv builders), `internal/fit` (ladder + secant search),
`internal/discordlint` (GIF/WebP/APNG parse, fix, report), `internal/jobs` (table, SSE, cancellation),
`internal/store` (blobs, results, sweeper), `internal/probe` (ffprobe + alpha detection).

## 4. Processing model

### 4.1 Universal decode → master frames

```
ffmpeg -hide_banner -nostdin -y -threads 0 [-c:v libvpx-vp9  # only for VP9-alpha WebM]
  [-ss A -to B] -i SRC [overlay inputs...]                  # trim = input seek (µs-precise), except animated WebP sources (filter-level trim below)
  -filter_complex "[0:v][setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,format=rgba | format=gbrap,setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,]  # 'premultiplied source' toggle, hoisted: yuva* sources unpremultiply at native depth then convert ONCE to rgba; RGB-decoded sources go through gbrap (§4.3 Alpha)
     [trim=start=A[:end=B],setpts=PTS-STARTPTS,]              # webp_anim sources only (Plan.FilterTrim): FFmpeg 9's demuxer decodes nothing after an input seek
     [setpts=PTS/S,]fps=FPS:round=down                        # speed, then a drop that never lengthens the clip; Frames = floor(Duration*FPS + 1e-4) for video (trim bounds are µs-precise), exact integer grid maths for image sequences (graph.sequenceFrames)
     [,format=rgba,format=yuva444p:color_spaces=bt470bg:color_ranges=tv,chromakey=color=0xYYUUVV:...:yuv=1,despill=... | format=rgba,colorkey=...]  # background removal (full-res, 4:4:4); the chromakey colour is the BT.601 limited-range YUV of the key and the keying format is PINNED to BT.601 limited range — the pin, not the rgba pass, makes a tagged (bt709) source key (Phase 5a, §4.3); N colorkey ops = N picked colours; on frames that already carry alpha the key is wrapped: split, alphaextract both mattes, blend=all_mode=multiply, alphamerge (§4.3)
     [,format=rgba[m1];[k:v]format=gray,scale=W:H:flags=bicubic[m1a];[m1][m1a]alphamerge | ,format=rgba,split[m1][m1m];[m1m]alphaextract[m1a0];[k:v]format=gray,scale=W:H:flags=bicubic[m1a1];[m1a0][m1a1]blend=all_mode=multiply[m1a];[m1][m1a]alphamerge]  # AI matte (Phase 5b): input k = the memoised gray PNG sequence; the matte becomes the alpha of opaque frames, is multiplied into frames that carry one (§4.3)
     [,format=gbrap,dilation=...,erosion=...[,dilation=... × grow],format=rgba]  # morph (Phase 5a): 3×3 close / grow on the alpha plane alone, hoisted with the keys and feather in stack order (§4.3)
     [,crop=w:h:x:y]                                          # incl. a resolved autocrop
     ,format=gbrap,premultiply=inplace=1,scale=W:H:flags=lanczos,unpremultiply=inplace=1,format=rgba
     [,pad=CW:CH:(ow-iw)/2:(oh-ih)/2:color=0x00000000][,transpose|hflip|vflip]
     [output fit: scale / pad / crop to Output.Width x Output.Height]
     [,format=rgba,reverse]                                   # after the output fit: buffers output-sized 4 B/px frames, bounded by jobs.Options.MaxMasterBytes (EZLG_MAX_MASTER_BYTES) in jobs' admitReversed — the graph never refuses on frame count
     [,format=rgba,split[f][r];[r]reverse[rr];[f][rr]concat=n=2:v=1:a=0]  # bounce (Phase 4): same slot as reverse, 2N frames / 2x duration, two buffered copies counted against jobs.Options.MaxMasterBytes (§4.3); at most graph.MaxBounces (8) bounce ops per recipe — each doubles the buffered frames (Frames saturates at math.MaxInt so jobs' overflow-safe estimate refuses the plan instead of reading a wrapped count as "unknown")
     [,format=rgba,drawtext / overlay stages]                  # final-canvas ops in the order given; windows enable='gte(t+0.0001,S)*lt(t+0.0001,E)'
     ,format=rgba"
  -f rawvideo -pix_fmt rgba /dev/shm/ezl/<job>/frames.rgba      + meta.json {w,h,fps,n,has_alpha,durations}
```

- Every source type enters through the same `-i` (FFmpeg 9 handles GIF, animated WebP, APNG, MP4/MKV/MOV/WebM). **Image sequences (as built in Phase 2)** use the **image2** demuxer, not concat: the store renumbers frames to `%06d.<ext>` (png/jpeg/webp/bmp/tiff only), the graph emits `-f image2 -framerate 1000/delayMs -start_number 1 -reinit_filter 0` plus a leading `scale=W:H:force_original_aspect_ratio=decrease` guard (fftools otherwise rebuilds the filtergraph on any frame size/format change and the fps stage loses frames — verified), and mixed-size sequences additionally pad onto a transparent W×H canvas (`pad=…:eval=frame`). The `delay` op re-times the whole sequence (uniform delays; per-frame delay lists are a later phase).
- **AVIF ingest (verified on FFmpeg 9.0.1, Phase 2):** ffmpeg's mov demuxer exposes a still AVIF as [colour, alpha(gray)] and an **animated** AVIF (avifenc and ffmpeg's own muxer alike) as **four** video streams — the one-frame primary item (colour, alpha) *first*, then the animation tracks (colour, alpha). `[0:v]` therefore decodes the still item. The probe picks the colour stream with the most frames and records `ProbeInfo.ColorStream`/`AlphaStream` (v:N indices; e.g. 2/3 for an alpha animation, 0/1 for a still); the graph reads `[0:v:C]format=rgba[c];[0:v:A]format=gray[a];[c][a]alphamerge` (or just `[0:v:C]` when opaque). `avifdec --index all` remains available as a fallback (enc.AVIFDecArgs) but is not needed.
- `has_alpha` = ffprobe `pix_fmt`/`alpha_mode` probe **plus** a real min-alpha scan of the master (GIF decoder always reports BGRA; VP9-alpha WebM only shows alpha with `-c:v libvpx-vp9`).
- **Alpha head for yuva sources (as built 2026-08-22, verified on FFmpeg 9.0.1):** ProRes 4444 decodes to `yuva444p10le`/`yuva444p12le` (`color_range` tv), and ffmpeg-made clips — Resolve exports included — store alpha on the **luma range** (12-bit 256..3750) because swscale range-converts alpha together with luma for > 8-bit YUV. The earlier head `format=gbrap12le,…` copied alpha same-depth (a +7 drift, no range expansion) and the later rgba conversion left transparent pixels at alpha **1** with full RGB underneath: bigger files, and autocrop at threshold 1 saw the whole frame as content. Any `yuva*` source now gets `[setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,]format=rgba` — native-depth unpremultiply, then a single conversion to rgba (exact 0/128/255 alpha, colour within 1). RGB-decoded sources (PNG/GIF/WebP/AVIF) are unchanged (`format=gbrap,setparams=…,unpremultiply=inplace=1`). Never route a yuva source through `gbrapNN` before rgba.
- Lower-fps candidates re-read `frames.rgba` with `fps=`; no re-decode. **Reverse (as built)** is ffmpeg's `reverse` filter, not a Go reorder of the file: emitted after the output fit and before the final-canvas ops, preceded by `format=rgba`, so it buffers output-sized 4 B/px frames — bounded by `jobs.Options.MaxMasterBytes` (`EZLG_MAX_MASTER_BYTES`, `admitReversed`). Frames and Duration are unchanged; text/overlay windows stay in output (reversed) time. See §4.3.
- **Frame-master cap (as built; moved to jobs alone 2026-09-13):** the only cap on a render's RGBA master (frames × W × H × 4 at *output* size) is `jobs.Options.MaxMasterBytes` — env `EZLG_MAX_MASTER_BYTES`, bytes, default 2 GiB = 2147483648; ≤ 0 or unparsable → default; clamped (logged) at `jobs.MaxMasterBytesCeiling` (`math.MaxInt64/16`) so the reservation arithmetic `need + max(need/8, 8 MiB) + (factor−1)·need` can never overflow into a non-positive reserve that skips the budget. `internal/graph` reports `Plan.Width/Height/Frames` and **never refuses a plan for its frame count** (`finish()` keeps only the `MaxDim`/`MaxPixels` frame check; `CompileDetect` skips even those). Until 2026-09-13 the compiler also refused any plan over a hard-wired 8 GiB, which blocked the *first still* of an untrimmed 2560×1440 × 704-frame clip ("expected master … 9.7 GiB exceeds the 8 GiB limit") before trim/crop/resize could be applied — a cap on a master that stills and proxies never build; the user had to trim in Resolve and re-import. Admission is now per consumer, in `jobs`: a **render** (`admitScratch`, at the start of the job, before ffmpeg runs) whose master would exceed the cap or the scratch filesystem is refused with an actionable message (the job ends in the error state with "the frame master would need 9.7 GiB (704 frames of 2560x1440 RGBA); the limit is 2 GiB — trim the clip, lower the fps or resize the output (or raise EZLG_MAX_MASTER_BYTES)"), and a render that fits reserves its estimate from the scratch byte budget (× `scratchFactor` — 2 for AVIF, frames, gifski and indexed/fit APNG, +1 for a fit budget on a fit format: gif/webp/apng/avif/png/jpeg/mp4/webm, never frames — out of a budget that is the scratch filesystem minus what the still/proxy memo dirs may hold, §4.3 Previews); **forward stills and proxies are not gated at all** — a still seeks one frame (`-frames:v 1`), a proxy is bounded by `MaxProxySeconds` (30 s) / `MaxProxyWidth` (720 px) / 15 fps, i.e. by constants, never by the source; **reversed/bounced previews**, and — because the render swaps in the one-frame plan *before* `admitScratch` and `-frames:v 1` does not shorten a `reverse` filter's decode — **static (png/jpeg) reversed renders**, are admitted by their reverse buffer (`admitReversed`; a bounce on top doubles `Plan.Frames`, a conservative bound). A bounce *alone* is not checked for a static render: its graph's first output frame is the forward branch's, and `-frames:v 1` ends the run before the reverse branch has buffered anything (measured on FFmpeg 9: a 600-frame 1080p bounce with `-frames:v 1` peaks at 4 MiB like a forward graph, a `reverse` graph at 4.8 GiB) — a bounced PNG of an untrimmed clip costs one decoded frame, while `[reverse, bounce]` sets `Reversed` and is checked. Trim/crop/resize/fit are non-destructive ops compiled into the single render pass and the master is measured at output size, so an emote render of a trimmed 4K clip is tiny — there is no "bake an intermediate" pre-phase (rejected; "Use as source" already chains results). The invariant the graph-cap removal relies on (written down in `compile.go`): **nothing allocates from `Plan.Frames` before admission** — every consumer is a comparison or a float (the frames-export cap, `clampStillTime`, `proxyBufferFrames`, enc's seek maths); a future `make([]T, plan.Frames)` breaks it and reviewers must catch it. The estimate is overflow-safe on every factor (`frameBytes` saturates at `math.MaxInt64`, so a crafted MP4 that probes to 4.29e9 s and plans 2.6e11 frames — or a bounce chain whose Frames saturated at `math.MaxInt` — is refused, never read as "unknown"). Blind spot, pre-existing and not closed here: a source with an **unknown frame count** (`Frames` 0 — a probe with neither Duration nor Frames/FPS) passes every byte cap with need 0; only the ENOSPC mapping and the preview timeouts bound it. Auto-crop recipes run the detection pass **before** admission (the still already memoised it, and detection is bounded by `autocropTimeout`), so "refused up-front" holds only after detection. With the graph cap gone the option is also the **only bound on the reverse/bounce RAM buffer** (the scratch budget sees disk only) — an operator raising it past host RAM gets OOMs, not refusals. `GET /api/capabilities` publishes `maxMasterBytes` and `scratchBudgetBytes` (0 = unlimited / unknown), and the SPA shows the live estimate under Render — `W×H · N frames · ~X of decoded frames (· about k× that on scratch)`, plus `· ~Y buffered by the reverse` for a reversed png/jpeg (the pre-cut count `admitReversed` judges) — which becomes an error note naming the frames/seconds that fit when any bound binds (§7): an untrimmed 4K source is trimmed / cropped / fitted in-app instead of being refused blind. Practical limits at the 2 GiB default (max frames = ⌊2 GiB / (W × H × 4)⌋ at *output* size; seconds at 30 fps):

  | Output size | Bytes / frame | Max frames | At 30 fps |
  |---|---|---|---|
  | 128 × 128 (emote) | 64 KiB | 32768 | 1092 s (18.2 min) |
  | 480 × 270 | 506 KiB | 4142 | 138 s |
  | 1920 × 1080 | 7.9 MiB | 258 | 8.6 s |
  | 2560 × 1440 | 14.1 MiB | 145 | 4.8 s |

  The cap binds large *outputs*: a full-resolution video export of a long clip still needs the streaming bypass (frames straight into the encoder, no master), which remains a later item.
- Duplicate-frame merge: `mpdecimate` **with `-fps_mode vfr`** (otherwise ffmpeg re-duplicates the dropped frames) — still a later-phase item; Phase 2 sequences are CFR at the image2 `-framerate`. **GIF output** merges its duplicate frames at the byte level since 2026-09-19 (`discordlint.MergeGIFHolds` on ffmpeg's `base.gif`, §4.2) — a Discord-safety step (§5.2 item 9), not a size option, and independent of this master-level item.
- Time base: GIF delays are whole centiseconds; browsers clamp delays ≤10 ms to 100 ms → minimum 2 cs, so GIF fps is **capped at 50** (other formats at 60) and otherwise left alone: ffmpeg's gif muxer runs at a 1/100 s timebase and rounds each frame's pts, so a 30 fps master gets 3/3/4 cs delays with exact total timing (Bresenham for free) and no frames are dropped or duplicated. ### 4.3 Editing ops

- **Background removal:** `format=rgba,format=yuva444p:color_spaces=bt470bg:color_ranges=tv,chromakey=color=0x913622:similarity=0.1:blend=0.05:yuv=1,despill=type=green:mix=0.6:expand=0.3` (blue screen: `color=0x29f06e`, `despill=type=blue:mix=0.6:expand=0.3:green=0:blue=-1`); pick-a-colour: `format=rgba,colorkey=color=0xRRGGBB:similarity=0.08:blend=0` — **one `colorkey` op per picked colour** (the Background card's "+ add colour" rows, up to 6, same similarity/blend; a colour picked twice is keyed once — duplicates collapsed, the second op would only redo the first's work), stacked through the alpha-keeping wrapper below so each removes its own colour; no new op kind. Eyedropper reads the still-frame PNG in the browser canvas; sliders re-render the still (~100 ms). Applied before scaling at full res. AI matting is the `matte` op (Phase 5b, the AI matte row below). **chromakey key colour (Phase 5a, 2026-10-08):** ffmpeg's `chromakey` keys on the 3×3-averaged (U,V) distance `sqrt((ΔU²+ΔV²)/(2·255²))` alone (luma ignored) and converts a `color=0xRRGGBB` with *full-range* RGB→YUV coefficients, while `format=yuva444p` off an RGB frame — and every BT.601 limited-range source — carries *limited-range* chroma: solid 0x00ff00 decodes to U 54 / V 34, the macro gives U 44 / V 21, 0.047 apart. So `similarity` below ~0.047 keyed nothing, the exact screen colour included, and the old default 0.2 keyed the subject on every non-green background (measured 2026-10-08, docs/reviews/background-removal-research-2026-10-08.md). The compiler now emits the key as the BT.601 **limited-range** `0xYYUUVV` with `yuv=1` — Y = round(16 + (65.481R + 128.553G + 24.966B)/255), U = round(128 + (−37.797R − 74.203G + 112.0B)/255), V = round(128 + (112.0R − 93.786G − 18.214B)/255), the values `format=yuva444p` produces from an RGB frame: green 00ff00 → `913622`, blue 0000ff → `29f06e`; Y is ignored by the filter and emitted for honesty, and the despill type still follows the RGB key — in a keying format **pinned to BT.601 limited range**: `format=yuva444p:color_spaces=bt470bg:color_ranges=tv` (`graph.chromaKeyFormat`; the `format` filter's `color_spaces` / `color_ranges` options, FFmpeg ≥ 7.0). The pin is mandatory and the leading `format=rgba` is not what fixes tagged sources: libavfilter's colorspace / range negotiation carries the source's tags across the rgba link, so a bare `format=yuva444p` re-encodes a yuv-decoded source with its own matrix (a bt709-tagged 1080p yuv420p screen capture, the common MP4 case) — measured on the host git build with a bt709 tv-range clip of 0x00ff00: `format=yuva444p` → U 42 / V 26, `format=rgba,format=yuva444p` → U 42 / V 27, both 0.047 from the 601 key, no key below ~0.05; `format=rgba,format=yuva444p:color_spaces=bt470bg:color_ranges=tv` → U 54 / V 35, as does the pinned format without the rgba pass, and every tagging tried (bt709 tv and pc, bt470bg, untagged, RGB-decoded, bt709 ProRes 4444) yields 54 / 35 and keys at 0.02 (bt470bg and smpte170m share swscale's 601 coefficients, the LimitedYUV formula; bt470bg is what SWS_CS_DEFAULT names). The leading `format=rgba` is kept per the Phase 5a contract: inline on opaque frames it goes through `ensureRGBA` like colorkey's; inside the alpha-keeping wrapper the stages are joined as-is (a redundant `format=rgba` is harmless). `MinSimilarity` stays 0.01 and now means what it says — the dead zone was the range mismatch, not a floor. *(Pixel tests, `internal/graph/keying_ffmpeg_test.go` `TestChromaKeyExactColourPixels`: the exact key colour keys at similarity 0.02 for green, blue and two custom colours from an RGB-decoded PNG and from bt709-tagged yuv420p sources at tv and pc range, with a subject square of another colour staying alpha 255, plus green from a bt709-tagged ProRes 4444 through the alpha-keeping wrapper; `TestMorphPixels`, `TestStackedColorKeysIntersect` cover the morph op and stacked colorkeys.)* **Defaults (Phase 5a):** chromakey similarity 0.2 → **0.1** (0.2 keyed the subject on every non-green background in the benchmark) and colorkey similarity 0.1 → **0.08** (colorkey's RGB distance at 0.05–0.08 beat chromakey everywhere but single-hue luma ramps, so Colour is the card's first classical mode and the stacked default); both live in `internal/graph/phase3.go` *and* `web/src/lib/state.svelte.ts` (`CHROMA_DEFAULTS` / `COLORKEY_DEFAULTS` — the SPA serialisers omit the default, so the Go zero value is what renders) and changed together under `jobs.PipelineVersion` 2026-10-08.1. A consequence of 0.1 worth knowing: `chromakey` scores each pixel by the mean distance of its 3×3 neighbourhood, so a screen pixel with three subject neighbours on a straight edge scores a third of the subject's chroma distance (~0.17 for a saturated subject such as 0xDC1E1E on green) — above 0.1 + blend 0.05 — and a **1-px rim of screen colour stays fully opaque** along hard edges (despilled to grey; autocrop boxes grow a pixel per side; the morph close cannot remove an opaque rim); the old 0.2 keyed that rim and a similarity around 0.15 keys it softly (partial alpha ~100). Visible on flat line art on a green screen; the tests pin it deliberately (`feather_ffmpeg_test.go` keyed-feather case, `jobs/phase3_e2e_test.go` autocrop table, `enc/phase3_ffmpeg_test.go` `TestCropDetectPlanReal`), the Screen hint in the card says so, and whether the Screen default should instead stay at 0.2 (where it never keyed the subject on a true green/blue screen and left no rim) is a user decision still open after the 5a review. **Keying on alpha-carrying frames (as built):** `chromakey`/`colorkey` *overwrite* the alpha plane, so when the incoming frames already carry alpha (source alpha, a merged AVIF alpha stream, transparent sequence padding, an earlier key) the compiler wraps the key — `split[k1][k1m];[k1m]alphaextract[k1a0];[k1]<key stages>,split[k1k][k1km];[k1km]alphaextract[k1a1];[k1a0][k1a1]blend=all_mode=multiply[k1a];[k1k][k1a]alphamerge` — so the two mattes are *intersected*: a Resolve ProRes 4444 export with Background removal keeps its source alpha instead of losing it. Opaque frames keep the bare `chromakey`/`colorkey`. Recipe semantics (`recipe.ChromaKeyParams`): `blend` 0 means the default 0.05 (a hard edge needs a small positive value such as 0.001); despill is emitted only when the key colour has a single dominant channel (green or blue) and is skipped otherwise, even with mix/expand set.
- **Feather (as built):** the `feather` op (`recipe.FeatherParams`: `radius` = Gaussian sigma in **source pixels**; the zero value means the default 3, valid 0.1–50, anything else is a compile error) softens the alpha edge with `format=gbrap,gblur=sigma=<R>:planes=8,format=rgba` — gbrap orders the planes G,B,R,A, so `planes=8` blurs *only the alpha plane*, and 8-bit gbrap↔rgba is a lossless plane repack (no range hazard). The stage is hoisted with the keying stages: emitted right after the keying ops and before any geometry (crop/autocrop/resize/canvas/flip/rotate), wherever it sits in the stack; multiple feather ops stack in stack order, interleaved with the keys per their stack order. Because it precedes the geometry, the radius scales with the image — a 3 px feather on a 720 px source is ~0.5 px after the emote fit. When the frame carries no alpha at that point the stage is skipped entirely — on an opaque source a feather that precedes every key is dropped, while one after a key always applies: blurring a constant-255 plane is a no-op that would waste two format conversions. Anchors ("tl"…"br") resolve X/Y against `text_w/text_h`. **Time windows** (text and overlays) are half-open `[S, E)` like trim: the graph emits `enable='gte(t+0.0001,S)*lt(t+0.0001,E)'` (`'gte(t+0.0001,S)'` for an open end, nothing for the whole clip; ffmpeg's `between()` is inclusive at both ends and is not used) — the 1e-4 s tolerance absorbs the µs rounding of the bounds (a frame-grid start such as 2/30 → 0.066667 lies just above its frame's raw timestamp, which a plain `gte` would skip) and the SPA floors "from scrubber" bounds to whole µs, so adjacent windows `[A,B)`/`[B,C)` never overlap and the frame at exactly E is not drawn. **Non-opaque colours (as built):** drawtext blends alpha *in place* on the rgba canvas, so any RRGGBBAA colour with AA < ff (the default box colour `00000080` included) is drawn on a transparent `color` source layer per element group (box → border → glyphs), faded with `colorchannelmixer=aa=AA/255` and composited with `overlay=format=auto:shortest=1:eof_action=repeat[:enable=<window>]`; opaque colours keep the in-place drawtext. - **Image overlay (as built):** overlay assets are ordinary uploads listed in `Recipe.Sources[1..]`; the graph emits one extra `-i` per asset (`[k:v]format=rgba[,fps=FPS][,premultiplied lanczos scale][,colorchannelmixer=aa=<opacity>],tpad=stop_mode=clone:stop=-1[ovk];[base][ovk]overlay=x=<anchor expr>:y=<anchor expr>:format=auto:shortest=1:eof_action=repeat[:enable='gte(t+0.0001,S)*lt(t+0.0001,E)']`). The `tpad` hold is mandatory (verified): without it `shortest=1` ends the whole output when a shorter overlay runs out, and without `shortest=1` a longer overlay extends it — with both, the base always decides the length and a finished overlay holds its last frame. Still images carried by image2/`*_pipe` demuxers get `-loop 1`; stills inside gif/apng/webp/mov containers reject `-loop` and rely on the hold.
- **Looping animated overlay (as built, verified on FFmpeg 9.0.1):** gif and video containers loop with `-stream_loop -1`; **animated WebP and APNG must use `-ignore_loop 0` instead — `-stream_loop -1` hangs FFmpeg 9's `webp_anim`/`apng` demuxers** (they never return after the seek-back), and with `-ignore_loop 0` the file's own loop count is obeyed (this app writes loop-forever files; a play-once file holds its last frame via the `tpad` hold). Non-looping overlays simply hold their last frame. Base alpha survives `overlay=format=auto` on an rgba main. VP8/VP9-alpha overlays force `-c:v libvpx`/`libvpx-vp9`; image sequences are not accepted as overlays (render them to an animation first). Stills: overlay inputs are not seeked — the main input keeps absolute timestamps (`-ss S -itsoffset …`) so overlays and `enable` windows line up exactly as in the render (`webp_anim` returns nothing after any `-ss`).
- **Trim on animated WebP sources (as built):** FFmpeg 9's `webp_anim` demuxer decodes nothing after an input seek, so for `webp_anim` sources the compiler emits a filter-level `trim=start=S[:end=E],setpts=PTS-STARTPTS` as the first stage (`Plan.FilterTrim`) instead of `-ss`/`-to`. Every `webp_anim` main-source plan, trimmed or not, is also flagged `Plan.SeekUnsafe` (FilterTrim implies it): stills and proxies never seek such plans — an untrimmed animated WebP still decodes in one unseeked ffmpeg run (jobs' `StillArgsFromStart` retry remains only as the guard for unexpected empty results), and a reversed proxy of one never seeks the tail, so its reverse-buffer admission counts the whole clip. Reversed stills of VFR animation sources (gif/apng/webp/avif, `Plan.SourceVFR`) decode from `TrimStart` instead of seeking by index; reversed *proxies* of the seekable ones (gif/apng/avif) get the plain grid-snapped tail seek whether trimmed or not. Every other source keeps the µs-precise `-ss`/`-to` input seek.
- **Crop to content (as built):** the `autocrop` op is resolved by jobs before compiling: a detection pass over the compiled **detection plan** (`graph.CompileDetect` + `enc.CropDetectPlanArgs`: source head, unpremultiply, trim/delay/speed/fps and the keying ops — chromakey / colorkey / feather / morph (Phase 5a), wherever those sit in the stack, since the compiler hoists them in front of the geometry; a green-screen clip with Background removal therefore resolves to its subject, not the opaque frame, and a cleaned matte to its cleaned box) samples ~5 fps and takes the union box — alpha sources: `alphaextract,lagfun=decay=1,bbox=min_val=<threshold-1>` (exact "alpha ≥ threshold" box; `cropdetect` was rejected because it tests row/column *averages* and rounds odd offsets), opaque sources: `cropdetect=limit=24:round=2:reset=0`. The parser reads only `[Parsed_bbox_`/`[Parsed_cropdetect_` log lines. The raw box is memoised under `<Scratch>/autocrop/<key>.json`, keyed by (source, detection ops, threshold; `autocropKeyVersion` 4 since Phase 5a — the chromakey fix changes the keyed picture for identical detection ops), and the padding is applied on read, so changing the padding never re-detects; the padded box is clamped to the frame and becomes an ordinary crop at the op's position; a flat/transparent clip resolves to the full frame. Concurrent requests for one key share a single pass, and the leader's pass continues (bounded by `autocropTimeout`, 5 min) even if the request that started it goes away, so the waiters — and the next request — get the result. Image sequences are detected through the same image2 input. The autocrop must precede any geometry op (crop/resize/canvas/flip/rotate); reverse/text/overlays neither reach the detection nor its key. Default suggestion for Emote (emoji render at ~22 px).
- **Reverse (as built):** ffmpeg's `reverse` filter (an odd number of `reverse` ops; two cancel), emitted after the output fit and before the final-canvas ops, preceded by `format=rgba`. The filter holds every frame until EOF, so it must see the *output-sized* frames: 4 B/px × W × H × frames, which `jobs.Options.MaxMasterBytes` (`EZLG_MAX_MASTER_BYTES`, `admitReversed` — the graph itself never refuses on frame count) bounds — a reverse in front of the fit would buffer source-sized frames (a 1080p 60 s clip fit to 128 px: 28 GiB for a 0.1 GiB master). Frames and Duration are unchanged; for reversed plans output time t maps to source time `TrimStart + (Duration − t)·Speed` (stills/proxies, `Plan.Reversed`). Trim applies in source time, text/overlay windows in output (reversed) time. A single-frame source is left alone.
- **Bounce (Phase 4, ezgif "bounce"/ping-pong):** `recipe.OpBounce`, no params — play forward, then backward. Emitted in the same slot as reverse (after the output fit, before the final-canvas ops), preceded by `format=rgba`: `split[f][r];[r]reverse[rr];[f][rr]concat=n=2:v=1:a=0`. The output is a **simple full copy: exactly 2N frames and 2× the duration** (the first and last frames are duplicated at the joins — predictable and cheap; the trimmed 2N−2 variant was rejected as a surprise for frame counts). The plan reports the doubled Frames/Duration, so the fit engine, the frames export and the sticker ≤ 5 s check all see the doubled clip. Memory: the split buffers two output-sized copies — jobs counts the master estimate ×2 against `jobs.Options.MaxMasterBytes` and the admission refuses what does not fit (each further bounce doubles again, saturating at `math.MaxInt`, which the overflow-safe estimate refuses rather than reading as unknown). Bounce and reverse compose in **stack order** (both emitted after the fit): a reverse in front of the first bounce reverses the forward half — `[reverse, bounce]` yields `rev(F)+F` (the clip opens on the *last* source frame) while `[bounce, reverse]` yields `F+rev(F)` — and reverse ops behind a bounce are dropped as identities (a full-copy bounce is a palindrome; reversing it reproduces it bit-identically, the reverse filter reusing the forward timestamps). A still source refuses bounce like it refuses reverse. Stills/proxies of a bounced plan are **never seeked** (decode from `TrimStart`, `SeekUnsafe`-like): output t < D maps to the forward pass, t ≥ D mirrors back. Autocrop is unaffected (bounce adds no pixels the forward pass lacks, like reverse it never reaches the detection). UI: a "Bounce (forward then back, doubles the length)" checkbox in the Speed card next to Reverse. `POST /api/still` (one PNG at t, ≤ maxW) and `POST /api/proxy` (the first `maxSeconds` of the op stack as a low-res animated WebP at ≤ 15 fps, lossy, with alpha; a single-frame plan with an animated overlay is proxied as an animation without the `fps=15` stage) share the compiler with the render, and **forward plans are not gated on frame count** (since 2026-09-13: the graph never refuses on it, a still seeks one frame and a proxy is bounded by `MaxProxySeconds`/`MaxProxyWidth`/15 fps, so an untrimmed 4K clip previews and is trimmed/cropped in-app — §4.1); only reversed/bounced plans go through `admitReversed`, and those whose buffer would exceed `jobs.Options.MaxMasterBytes` are refused (400, "trim the clip"; for a reversed proxy the buffer is the tail enc seeks to, or the whole clip for `Plan.SeekUnsafe` animated-WebP sources, which are never seeked). Follow-up, not done: a reversed/bounced *still* of an untrimmed large clip is still refused although it could be served as a forward still at the mapped source time (`TrimStart + (Duration − t)·Speed`) without buffering anything; a preview semaphore of max(2, concurrency) bounds the ffmpeg runs; in-flight requests are de-duplicated by memo key (one render, every waiter gets the file). Results are memoised under `<Scratch>/stills` and `<Scratch>/proxy`, bounded by count (`MaxStills`) **and** bytes (`MaxStillsBytes`/`MaxProxyBytes`; oldest evicted), and the scratch budget for renders subtracts what those dirs hold.
- **Alpha:** the user's Resolve exports are **premultiplied** (matted with black), so the "premultiplied source" toggle defaults on for ProRes; the graph inserts `setparams=alpha_mode=premultiplied,unpremultiply=inplace=1,format=rgba` immediately after decode for `yuva*` sources (ProRes 4444 decodes as `yuva444p10le`/`12le`; `unpremultiply` takes the yuva444p 9–16-bit variants directly, so the divide runs at native depth and the frames are converted to 8-bit RGBA exactly once — see §4.1 for why the earlier `format=gbrap1Nle` head was wrong for ffmpeg-made ProRes: alpha on the luma range, transparent pixels left at alpha 1) and `format=gbrap,setparams=alpha_mode=premultiplied,unpremultiply=inplace=1` for RGB-decoded sources, *before* any keying or scaling. Otherwise (WebP/APNG/AVIF need straight alpha) edges get dark fringes on light backgrounds. **The `setparams` tag is required on FFmpeg ≥ 8:** libavfilter now negotiates `AVFrame.alpha_mode` across links; `unpremultiply` demands premultiplied input but ProRes/rawvideo/most decoders tag frames `unspecified`, so without the tag ffmpeg auto-inserts `premultiply_dynamic` in front (`-loglevel verbose`: "auto-inserting filter 'auto_premultiply_dynamic_N'") and the pair cancels out — the toggle silently became a no-op (verified 9.0.1: edge pixel R=64/A=64 stayed R=63; with the tag R=253). Its position relative to the `format=` stage does not matter (the auto-inserted conversion passes the mode through). `internal/graph/alpha_ffmpeg_test.go` checks this at pixel level whenever ffmpeg is on PATH. A heuristic (edge pixels dark over white) pre-selects the toggle for other sources. Scale is wrapped in `format=gbrap,premultiply/…/unpremultiply`, which needs no tag: `premultiply` requires straight input, which is what `unspecified` degrades to (and after the hoisted unpremultiply the frames are tagged straight anyway). GIF = matte-then-threshold; WebP/APNG/AVIF keep 8-bit straight alpha.

### 4.4 Files in and out — /input picker, /output save (Phase 4)

Two optional bind mounts let files skip the browser: `/input` (read-only source folder) and
`/output` (bulk sink; also where the Discord test kit writes). Paths are configurable —
`EZLG_INPUT` (default `/input`), `EZLG_OUTPUT` (default `/output`). The server checks both **once
at startup** (directory exists, `/input` readable, `/output` writable) and reports the outcome in
`GET /api/capabilities` as `features.inputPick` / `features.outputSave`; the endpoints answer
**503** when their feature is off. Listing/writing is per-request — files added to a mounted
`/input` show up without a restart — and a directory that stops being usable *after* startup
(mount vanished, permissions, disk full) maps onto the **same operator-facing 503** as the
startup check, never a 500 leaking server-side paths (capabilities keeps reporting the startup
outcome until a restart).

- `GET /api/input` → `{"files": [{"name": "clip.mov", "size": 123, "mtime": "<RFC 3339>"}, …]}` —
  a **flat** listing (no recursion), filtered to extensions the pipeline can decode, name-sorted,
  capped at 500 entries, always an array (never null). (The Phase 4 draft sketched a bare array;
  it ships wrapped in `{"files": …}` for consistency with `/api/fonts` and the `{"error": …}`
  error shape.)
- `POST /api/sources/from-input` `{"name": "clip.mov"}` → 200 `recipe.Source`: ingests the file
  exactly like an upload (copy into the blob store, sha256 dedupe, probe) — re-picking a file, or
  picking one that was also uploaded, yields the same source hash. `name` must exactly match a
  listed entry (anything containing a path separator, or not in the listing, is 404 — that is the
  whole path-traversal defence); 503 when `/input` is off; a file over the upload size limit
  (`EZLG_MAX_UPLOAD_MB`) is 413, exactly like an upload of the same bytes.
- `POST /api/results/{recipeHash}/save` `{"file": "<name from the result manifest>", "name":
  "<optional base name>"}` → 200 `{"name": "<final file name>"}`: writes that result file into
  `/output` under a **collision-safe** name (`base.ext`, `base-2.ext`, `base-3.ext`, …; the base
  defaults to the download name the file would get with `?dl=1`) and returns the name actually
  used — 409 never happens. 404 for an unknown result or file name; 503 when `/output` is off.
- Web: the result card (and each batch row) gains "Save to /output" when `features.outputSave`;
  batch adds "Save all to /output". The upload zone offers "… or pick from /input" when
  `features.inputPick`. There is no zip-of-everything endpoint — downloads stay per-file,
  `/output` is the bulk sink.

### 5.2 Why transparent files break on Discord (from `discord/lilliput` source)

Every inline preview (attachments, emoji, stickers) is decoded and re-encoded server-side by lilliput (giflib + libwebp + libavif). Production is not exactly the public repo — item 9 does not reproduce with it — so an upload test outranks the source. Known quirks as of Sep 2026:

1. GIF frame **without a Graphic Control Extension** → transparent index uninitialised (usually palette index 0) → wrong/flickering colours (issue #267). **Fixed upstream 2026-08-18** (lilliput 83a6bd3, PR #297 — this list used to say "fix PR #276 unmerged"); which lilliput Discord deploys is unknown, so the rule stays mandatory.
2. Canvas background alpha is decided **only from frame 0's GCE**: if frame 0 has no transparency flag the canvas is opaque (LSD background colour) and later transparent frames get a solid (often black) background — the classic symptom. The encoder also deletes transparency for a frame whose transparent index equals the LSD background index when the background is opaque.
3. Disposal 0 (unspecified) treated as "do not dispose"; disposal 3 (restore previous) only supported since Apr 2025; disposal/background handling churned May 2025.
4. Missing NETSCAPE2.0 loop block → loop count 1 (plays once) after GIF→WebP transcode.
5. Frame-diff optimised GIFs / per-frame local palettes have produced "random colour per frame" glitches (local-palette corruption fixed Jun 2025; still cited in 2025 reports).
6. WebP: alpha is dropped if the VP8X container **ALPHA flag** is unset while frames carry alpha (PR #296 open); wrong VP8X canvas dims broke uploads; Discord's EXIF stripper used to corrupt animated WebP metadata (fixed) → emit no EXIF/XMP/ICC.
7. First frame is shown as the still whenever animation isn't playing (autoplay off, reduced motion, hover previews) → a blank first frame looks broken.
8. ffmpeg foot-guns: legacy `libwebp` encoder → ghost trails; webp muxer `-loop` default 1; apng muxer `-plays` default 1; the gif encoder's default `-gifflags +offsetting+transdiff` is wrong for frames with transparency, twice over (encoder bugs, not Discord quirks — the pixels are wrong in every decoder): (a) `gif_crop_translucent` crops such a frame to its opaque bounding box but its left / right column scans skip the box's bottom row (`for (i = *y_start; i < y_end; i++)`, where `gif_crop_opaque` has `y <= y_end`), so the part of that row sticking out past the rows above is cut off and turns transparent — a one-row-tall opaque area degenerates to a 1×1 rect; (b) diffing and disposal are chosen per frame, so a fully opaque frame inside a transparent clip is diffed against a frame that was disposed (holes) and keeps disposal 1 (it stays under the next transparent frame). Alpha GIFs are therefore encoded with `-gifflags -offsetting`; when the output mixes both kinds of frame in a way the encoder renders wrong (`discordlint.GIFNeedsCompleteFrames`) it is encoded again with `-gifflags -offsetting-transdiff` and `discordlint.DisposeCompleteFrames` sets every frame's disposal to 2 (§4.2 GIF row). Identical in FFmpeg 8.0, 9.0.1 and master as of 2026-09-19 (last commit to `libavcodec/gif.c` 2025-12-23); the fix for (a) is `<` → `<=` in both loops. Not reported upstream: code.ffmpeg.org had no hit for `gif_crop_translucent` on 2026-09-19 (trac's search sits behind a bot wall).
9. **Production drops a frame that does not change the composited picture, folds its delay into the previous frame — and loses the dropped frame's disposal with it** (user-verified 2026-09-19 with a six-variant upload test of pixel-identical files, docs/reviews/discord-stack-test-2026-09-19.md). When that frame carried the disposal-2 clear the next pose depends on, the clear never happens and new frames draw on top of old ones ("stacking"). `gifsicle`'s optimiser manufactures exactly such frames from **holds in transparent animations**: a run of identical frames followed by a frame that needs pixels cleared becomes one disposal-1 frame with the long delay plus the *last* duplicate kept as a separate short disposal-2 frame — all-transparent under `-O2`, a redraw of the same pixels under `-O1` — whose only job is to erase the area. `-O1`, `-O2` and `-O3` all do it and no flag avoids it. **Not reproducible with public lilliput** (HEAD b337020 and four older commits keep every frame), so it cannot be tested locally — the `gif.noop-frame-disposal` rule of §5.3 is the contract. The same test cleared the other suspects: mixed disposal 1/2, sub-rect delta frames and a per-frame transparent index all render correctly, as do all-disposal-2 files (cropped or full canvas).
10. lilliput's GIF **encoder** caches nearest-palette lookups per 15-bit colour (`palette_lookup`, `giflib.cpp`) and reuses the cache while the palette bytes are unchanged — but a **per-frame changing transparent index** moves the slot that must not be used, so a cached answer can land on the new frame's transparent index: single-pixel holes in the GIF→GIF path (verified). Every gifsicle write re-picks the transparent index per frame, so every gifsicle-processed output has a varying index. Cosmetic, and not fixed here — the varying-index variants of the item 9 test rendered correctly.

### 5.3 Encoder rules → enforced by `internal/discordlint` (lint → fix → verify)

**GIF**
- GCE on every frame **including frame 0**.
- If any frame is transparent: frame 0's GCE has the transparency flag set (allocate an unused index if needed) and LSD background index = that transparent index. If nothing is transparent, LSD bg index ≠ any frame's transparent index.
- Explicit disposal 1 or 2 on every frame; never 0 or 3.
- **No frame that leaves the picture unchanged but changes the disposal** — `gif.noop-frame-disposal` (2026-09-19, §5.2 item 9; runs right after `gif.disposal`; **error** for Discord targets, **warning** for target none — the `gif.global-palette` split; the level only decides `Report.OK`, the repair below runs at either level). The linter simulates the GIF per spec on a canvas where 0 = cleared and any drawn pixel is an opaque colour value: pixels equal to the frame's transparent index (GCE transparency flag set) are skipped, colours come from the local table else the global one, disposal 2 clears the frame's rect to 0, disposal 0/1 leave it, disposal 3 restores the rect to what it was before the frame was drawn. With P[k] = canvas after drawing frame k and D[k] = canvas after then applying its disposal: frame k ≥ 1 is a **no-op** when P[k] == P[k−1]; a no-op is **harmless** when D[k] == D[k−1] (dropping it and adding its delay to k−1 changes nothing) or when it is the **last** frame (its disposal never matters — the canvas is reset on loop restart); otherwise it is **unsafe**, and any unsafe frame fails the rule. Cheap equivalent for disposals 0/1/2: with C[k] = frame k's rect if disposal 2, else empty, D[k] == D[k−1] iff every pixel of P[k−1] inside the symmetric difference of C[k] and C[k−1] is already 0; when either frame uses disposal 3 and (disposal, rect) differ, the frame counts as unsafe. The detail names the frames and says why; not fixable at byte level (needs a re-encode). The analysis **ends at the first frame it cannot judge**: a frame whose rect sticks out of the logical screen (decoders clip, grow the screen or reject the file — nothing is clipped here), a **reserved disposal value 4–7** (Chromium/Firefox read 4 as restore-previous, ffmpeg/gifsicle as leave), undecodable LZW data, or the decode cap (2³¹ decoded pixels per walk). The frames before it are still analysed (the canvas spans the bounding box of their rects): unsafe frames among them fail the rule and the detail adds "not analysed from frame N on"; otherwise the check **passes** with that note. A canvas over the 16 M-pixel cap is not analysed at all and also passes with a note — a known limitation (§11): "pass" then means "not judged", at error level too. Harmless no-ops are legal and common — ffmpeg's raw alpha output is all disposal 2 with one duplicate frame per held tick (the reported clip: 118 frames for 17 distinct pictures, all 101 duplicates harmless no-ops; merged 118 → 17) — and are merged anyway (`MergeGIFHolds`, below), because gifsicle's optimiser is what turns them into unsafe ones.
- NETSCAPE2.0 loop block present; count 0 for every Discord target (Discord plays once otherwise). For non-Discord output (target none) the user's `Output.Loop` (N = play N+1 times) is honoured and only the block's presence is enforced. Delays ≥ 2 cs (guaranteed by the 50 fps cap; the muxer's centisecond rounding gives exact Bresenham timing).
- Single global palette, no local colour tables (enforce via `gifsicle --colors N`; fail lint otherwise). No interlacing; strip comment/plain-text/app extensions.
- 1-bit alpha via matte-then-threshold; first frame representative (warn if empty).
- Fixer scope: add/patch GCE, flag/index, delay, disposal 0→1, LSD bg index, NETSCAPE, strip extensions. **Cannot** fix disposal 3, interlace, full palette with no free slot, local tables, unsafe no-op frames → re-encode ladder (`jobs.lintGIF` — every plain render, the lossless fast path and gifski; needs gifsicle; re-linted after every rung, stops at the first rung without a structural failure; rebuilt 2026-09-19). A **structural failure** (`jobs.hasStructuralError`) is a failed error-level check other than a byte/dimension/duration limit, **or a failed `gif.noop-frame-disposal` at any level** — the hold rule is only a warning for target none, but the file is repaired all the same, so the ladder runs for every target:
  1. `gifsicle -O2 --lossy --careful --colors N` — unchanged, but **skipped when `gif.noop-frame-disposal` is the only structural failure** (the optimiser would only make the same frames again).
  2. **Repair:** coalesce with `gifsicle -U --disposal=background` and *no* `-O` (`enc.GifsicleOptions{Unoptimize, NoOptimize, DisposeBackground}`: every output frame is a full-canvas frame with disposal 2; under `-O` the optimiser overrides `--disposal`). **gifsicle gets this wrong at exit 0 in two cases (measured 2026-09-20, gifsicle 1.96), so the step is prepared and checked:** (a) its unoptimiser decides from the *first* frame whether the canvas is transparent at all — unless that frame declares a transparent index *and uses it*, every coalesced frame comes out opaque and the clip's later transparency is painted over with the background colour (a clip that starts on an opaque picture; also a first frame that is opaque and smaller than the screen). A file that shows the background anywhere (`discordlint.PlayGIF` … `ShowsBackground`) is therefore handed over with a transparent 1×1 zero-delay **lead-in frame** (`discordlint.PrependTransparentFrame`: transparent index 0 of the *global* table — with a local table gifsicle refuses to unoptimise at all) that the frame selection `#1-` right after the input drops again (`enc.GifsicleOptions.SkipFirstFrame`); where `-U` worked before, the output is byte-identical, and an opaque file is left alone. (b) With local colour tables, or more than 256 colours in one composited picture, it prints "too complex to unoptimize", coalesces nothing and *still* stamps disposal 2 on every frame. So the coalesced file is **played and compared with the input** (`GIFPlayback.Same`: the same pictures — colours and transparency — for the same time each, whatever the frames that produce them); if it differs the step is an error and the caller keeps the bytes and the failing report it had (for a Discord target the `--colors` rung has merged the local tables by then, so the repair usually goes through; for target none the file is delivered as it came, the rule still a warning). The re-optimised file of step B is compared too when nothing lossy ran, and the coalesced one kept if it differs. An input the player cannot judge (a frame outside the logical screen, a reserved disposal, broken pixel data, the analysis caps) is repaired **unchecked** — it still gets the lead-in frame, since nothing says it is opaque — and so is a coalesced file that is merely too large to play (`discordlint.ErrAnalysisCap`: full-canvas frames cost far more than the optimised input's sub-rectangles; held frames cost nothing, the player skips byte-identical repeats); a result that cannot be played for any other reason is refused. Measured against real gifsicle on 72 corpus/synthetic files and 3,000 random GIFs: 0 false refusals, 0 wrong results passed → `discordlint.MergeGIFHolds` → `gifsicle -O2 --careful [--lossy]`. With the holds merged the optimiser has no run to split, so it makes no clear-only frame.
  3. **Coalesced:** coalesce → `MergeGIFHolds` and stop — full-canvas frames, every frame disposal 2 (costs bytes). Used when rung 2's `-O2` output still has a structural failure or the pass failed. It belongs to the all-disposal-2 family of the upload test, of which cropped/varying-index (file 4), cropped/constant-index (file 5) and full-canvas/constant-index (file 6) were verified; **this combination — full canvas with gifsicle's per-frame transparent index — has not been uploaded**.

  The earlier rungs `-U -O2 --careful` and plain `-U` are gone. Measured 2026-09-19: plain `gifsicle -U` writes a disposal 0/2 **mix** — not "coalesced full frames, disposal 2", as this section used to claim — and keeps the unsafe duplicate frames; `-U -O2` re-creates them. Never end a rung in plain `gifsicle -U`. The optimize preset, `optimizeFit`'s candidates and the render fit's **default-encoder** GIF candidates do not walk the ladder: they run rungs 2–3 on their own output (`jobs.repairIfOnlyHolds`) when the hold rule is their **only** structural failure — at any level, so for target none too (§4.2 GIF → GIF). The render fit's **gifski** candidates do walk the whole ladder (`jobs.gifLadder`, the function behind `lintGIF`, with per-candidate scratch names and no `--lossy`; `PipelineVersion` 2026-09-19.3): gifski's local colour tables fail rules only rung 1 can fix, so without it practically no full-size gifski candidate could be chosen (§4.2 gifski row). The `desc` note "held frames re-encoded for Discord" is set only when the file entering rungs 2–3 really failed the hold rule — they double as the generic re-encode. Rungs 2–3 are `jobs.repairGIFHolds`; if its coalesce pass fails the caller keeps the bytes and the report it had. **Known cost (documented, not fixed):** step B re-applies the caller's `--lossy` (and `--colors`/`--dither`), which for the optimize preset and the fit candidates means a *second* lossy pass over bytes that are already lossy — second-generation loss, although the `desc` names one `lossy N` — and a repaired candidate costs about 2.3× the gifsicle work (coalesce + re-optimise on top of the original pass), for every candidate of a source with holds. Coalescing the source once and running one pass per knob was measured within 0.3 % of the size and would avoid both; not built.
- `discordlint.MergeGIFHolds(data) (out, merged, err)` — the hold merge of §4.2 and of rungs 2–3: drops every **harmless** no-op frame (k ≥ 1, a harmless last frame included) and adds its delay to the surviving predecessor's GCE. Guards — a frame is never merged when the surviving predecessor has no well-formed GCE to carry the delay (none at all, or a block too short for the delay field), when the summed delay would exceed 65535 cs, or when either frame has the user-input flag; delays are summed as written (a 0/1 cs delay adds 0/1 cs, not the 10 cs browsers show). **Unsafe** no-ops are left untouched (the rule reports them, the repair re-encodes) — with one exception, the **tail step**: when dropping the trailing frames turns an unsafe no-op into the *last* frame, its disposal stops mattering (the canvas is reset on loop restart) and it is merged too; this step runs only when **every** frame was analysed. Merging stays inside the analysed prefix: everything from the first frame the walk cannot judge (outside the logical screen, reserved disposal 4–7, undecodable LZW, an analysis cap) is left byte-for-byte as it was. A dropped frame takes its GCE block(s) with it; every other byte round-trips exactly; nothing merged → the input slice itself and `merged == 0`; `err` only for unparseable input. Where it runs: on ffmpeg's `base.gif` before the gifsicle post-pass (`jobs.encodeGIFAt`, single renders and fit candidates; best effort — a failure is logged and the lint has the last word) and on the coalesced file inside `jobs.repairGIFHolds`. Any new `gifsicle -O` pass over freshly encoded frames must merge first. The other `-O2` passes do **not** merge first — the gifski finite-loop pass (gifski folds identical frames itself: 118 → 21 frames on the reported clip, no unsafe frame after the loop pass), the ladder's `--colors` rung, the lossless fast path and the optimize preset (frame selection and crop happen inside the same gifsicle call) — and are covered by lint + repair.

### 5.4 Presets and fit-to-size

Byte caps are hard, expressed in KiB, with a 1–2 % margin. Fit = parallel ladder from one master + secant search on log(size) over the format's quality knob (GIF: `gifsicle --lossy` 0–200, or gifski `--quality` 100→1 with the gifski encoder; WebP: `-q` 95–10; APNG: colours 256→64; AVIF: `-q`; MP4: x264 CRF searched 12..40 (mild probe = the effective CRF — Output.Quality-as-CRF clamped into the window, default 20 — harsh 40); WebM: vp9 CRF searched 15..55 (mild = effective CRF, default 30; harsh 55) — CRF is monotonic on log(size), so the same secant applies), 2 probes per rung (mild/harsh), skip rungs whose harsh probe is over budget, early-exit rungs whose mild probe fits, ≤ 5 iterations otherwise. Winner = mildest rung that fits; 2 runner-ups shown as alternatives; report the binding knob ("fit at 20 fps · 128 colours · lossy 40").

Perceptual cost order (cheapest first): autocrop/merge duplicates → ordered dither instead of error diffusion (−15–20 %) → lossy 30–80 (−20–40 %, near-invisible) → fps 30→24→20→15 → colours 256→128→64 → heavy lossy / alpha_q → downscale (never for stickers) → trim duration (ask).

## 8. Speed strategy

Ingest: XHR multipart (no tus/chunking), streamed to disk with SHA-256 computed server-side (WebCrypto is unavailable on plain HTTP), deduped by hash; probe + still + proxy pre-warmed the moment the upload lands; `/input` picker skips upload. Processing: one decode + one filter pass per render into the RGBA master on tmpfs; every encoder/candidate/format fans out from it under a `NumCPU/2` semaphore with `-threads 0`; encoder knobs pinned to fast settings (heavy squeezes — `-m 6`, zopfli, `apngopt` — behind an explicit button); GIF→GIF edits never decode; stills served from the master when it exists (Go `image/png`, no ffmpeg spawn); stills and Play proxies memoised on scratch behind admission (preview semaphore max(2, concurrency), in-flight de-duplication by memo key, count- and byte-bounded memo dirs — §4.3 Previews); results memoised by recipe hash. Delivery: files written once, served immutable, direct links, zips STORE'd, `/output` mount.

   **Verified ffmpeg facts** (FFmpeg 9.0.1 in the image; Phase 1–3 builds, last updated 2026-10-08 with the Phase 5a keying facts — each is pinned by a test or by the build-time `scripts/check-tools.sh` guard):
   - `setparams=alpha_mode=premultiplied` must precede `unpremultiply` (FFmpeg ≥ 8 otherwise auto-inserts a cancelling `premultiply_dynamic`; `internal/graph/alpha_ffmpeg_test.go`).
   - ffmpeg-made ProRes 4444 (`yuva444p12le`, range tv) stores alpha on the **luma range**; `format=gbrap12le` copies it same-depth (+7, no expansion) and the later rgba conversion leaves transparent pixels at alpha 1. `unpremultiply=inplace=1` runs on `yuva444p10le`/`12le` directly and a single `format=rgba` afterwards yields exact 0/128/255 alpha with colour within 1 (§4.1 alpha head).
   - `chromakey`/`colorkey` overwrite the alpha plane — the keying wrapper (split / alphaextract / `blend=all_mode=multiply` / alphamerge) is what keeps source alpha (§4.3).
   - `chromakey` converts `color=0xRRGGBB` with full-range RGB→YUV coefficients and keys the limited-range chroma `format=yuva444p` produces (green: U 54 / V 34 in the frame vs 44 / 21 for the key — 0.047 apart, so nothing below that similarity keyed, the exact colour included); `color=0xYYUUVV:yuv=1` with the BT.601 limited values keys the exact colour at 0.02 (measured 2026-10-08 on the host git build, §4.3) — **only in a keying format pinned to BT.601 limited range** (`format=yuva444p:color_spaces=bt470bg:color_ranges=tv`): libavfilter's colorspace / range negotiation carries a source's tags across an rgba link, so `format=rgba,format=yuva444p` re-encodes a bt709-tagged capture with its own matrix (green → U 42 / V 27, 0.047 from the key, no key below ~0.05; bare `format=yuva444p` → U 42 / V 26), while the pinned format gives U 54 / V 35 for bt709 tv / pc, bt470bg, untagged, RGB and bt709 ProRes 4444 sources alike. Pinned by `internal/graph/keying_ffmpeg_test.go` `TestChromaKeyExactColourPixels` (RGB PNG, bt709 tv, bt709 pc, bt709 ProRes 4444, all at 0.02).
   - `erosion` / `dilation` have no `planes` option (`ffmpeg -h filter=dilation`: `coordinates`, `threshold0..3`); on gbrap, `threshold0..2=0` freeze G/B/R and the default `threshold3` leaves A a plain 3×3 min/max (§4.3 Morph; pixel test: colour planes byte-identical).
   - `webp_anim` demuxer: decodes nothing after an input seek (`-ss`), for the main input and overlay inputs alike (filter-level trim; unseeked stills/proxies); `-stream_loop -1` hangs `webp_anim` and `apng` (use `-ignore_loop 0`, which obeys the file's own loop count).
   - `overlay=…:shortest=1:eof_action=repeat` plus `tpad=stop_mode=clone:stop=-1` on every finite overlay input: the base decides the length, a finished overlay holds its last frame.
   - `drawtext` blends alpha in place on an rgba canvas — semi-transparent colours need a separate `color` layer + `colorchannelmixer=aa=` + `overlay` (§4.3 Text).
   - `reverse` holds every input frame until EOF: memory = frames × W × H × 4 at the point it sits → after the output fit, under `jobs.Options.MaxMasterBytes` (`admitReversed`; since 2026-09-13 the graph never refuses on frame count — the buffer admission is jobs' alone).

## 11. Risks

- Discord's lilliput/media proxy keeps changing (open PRs, 2025 disposal churn) and production is not the public repo (§5.2 item 9 does not reproduce with it) → linter rules are data, versioned, re-validated per phase; only an upload test is authoritative.
- FFmpeg 9.0.1 is weeks old (new webp_anim decoder) → fallbacks documented (`anim_dump`, `avifdec`), pin the tarball hash.
- Frame master sizing for long/hi-res chat exports → frame cap + streaming bypass + `shm_size` guidance.
- Animated AVIF alpha and GIF stickers unverified on Discord → labelled experimental; APNG stays the sticker default.
- Frame-diff GIF optimisation may still glitch through Discord in edge cases → verify step + coalesce fallback (costs bytes on a tight 256 KiB fit). One such case surfaced 2026-09-19 — gifsicle's clear-only frames from holds, §5.2 item 9 — and is addressed by merging holds before gifsicle (the .2 pipeline's output for the reported recipe was byte-identical to upload-verified variant 2 of §9b; the .4 output differs by the restored edge pixel and frame 0's rect, its pre-gifsicle form equals verified variant 6, and it has not been uploaded itself), `gif.noop-frame-disposal` and the hold repair (§5.3). What is verified by upload is that six-variant matrix and nothing else: the repaired / coalesced forms (full canvas + per-frame transparent index together) and other inputs have not been uploaded.
- Known limitations of the hold fix (documented, not fixed; §5.3): (a) **analysis caps** — a GIF whose analysed frames span more than 16 M canvas pixels is not analysed, and a walk stops after 2³¹ decoded pixels; the rule then **passes** with a "not analysed" note (after spending the lint time up to the cap) and `MergeGIFHolds` merges nothing / only the analysed prefix. Far beyond any Discord upload, but a pass there means "not judged". The same holds from the first frame outside the logical screen or with a reserved disposal (4–7) on. (b) **second-generation lossy + cost** — in the optimize preset and the fit candidates the repair's re-optimise step applies the caller's `--lossy` a second time to already-lossy bytes and costs ~2.3× the gifsicle work per repaired candidate.
- Premultiplied vs straight alpha can't be auto-detected reliably → toggle + heuristic + dark/light preview.
- LAN-only assumptions (no auth/TLS) — keep behind the LAN or a reverse proxy.
- Licensing: gifski (AGPL) and gifsicle (GPL) are exec'd, not linked; cgo-linking gifski later would make the binary AGPL-derived.
- drawtext escaping/fonts (use `textfile=`, bundle fonts, add noto for CJK/emoji).

## 12. Rejected alternatives

Client-side WASM (ffmpeg.wasm/wasm-vips/gifski-wasm); Python/FastAPI main backend (Python survives only as the stdlib-`http.server` + onnxruntime matte sidecar of Phase 5b — no rembg, no torch, no FastAPI; §6); Node/Bun + sharp; Redis/Celery/SQLite job queues; ezgif-style per-tool pages with re-encoded intermediates; gifski as default GIF encoder; legacy ffmpeg `libwebp` encoder; CUDA-first pipeline; ImageMagick for animation; libvips via cgo; tus/chunked uploads; client-side hashing; WebSockets (SSE suffices); linuxserver/jrottenberg nvidia base images (700 MB–1.3 GB vs ~500 MB trixie-slim + static builds); APNG for chat/emoji; Lottie stickers; forking existing projects (ConvertX, OmniTools, imgproxy, gifcurry — borrow ideas only).
